# execution.semantic_planning

## 洞察语义规划

当前工作是先想清楚如何回答本轮全部业务问题，再选择精确 Schema 材料或编写代码。必须调用 `plan_runtime_semantics`，按工具的 JSON Schema 提交确定的结构化语义定义；普通文本总结不能代替这份对象。`questions` 中每个已有 `question_id` 恰好一项，多个洞察方向在该问题内展开事实、计算与判断，不新增问题编号。

- 对每个问题说明分析对象与统计总体、时间归属、分组和比较边界。用户明确给出的多个时间窗口或对象都要保留，不把其中一个当作全部口径。
- `facts` 按实际分析需要拆解并承接 `business_questions.required_business_facts` 的业务含义，`fact_id` 在本问题内唯一，供后续依赖引用。能够从已选 Schema 确认的事实用 `direct` 和真实的 `datasource_id` / `fields` 标记；计算或转换产生的事实用 `derived`，通过 `derived_from_fact_ids` 引用已有事实，或通过 `source_bindings` 直接绑定实际输入字段，在计算规则中说明转换；仍不能确认的用 `unresolved` 和原因标记，不能臆造字段。`source_bindings.role` 描述字段的分析用途，例如度量、维度、时间或关联键。实际需要跨源时引用 Schema 中已有的 `relationship_ids`，未知关系作为待核实项保留。
- 对已经选择计算的量，`calculation_rules` 记录业务含义、实际输入要求、输入粒度、输出分组、单位及依据；用户、规则或 Schema 提供的公式原义保留，不另外生成一份要后续翻译的算法伪代码。唯一可执行算法在正式程序中定义为原生计算定义或一个 Python 函数，并由保存的执行结果共同供表达消费。单位量、率值等非可加量须明确业务汇总含义和数量口径；未知含义保留未知。开放式问题不必预列全部指标或报告章节。`basis` 区分用户要求、会话规则、Schema 定义、可解释的分析推导和仍未确定的口径。
- 计算需求用业务含义、输入粒度、输出范围与单位承接。实体数量与记录数量、分组范围与展示归属要明确区分；实际输入、分组字段及计算结果依赖由正式程序中的唯一执行定义声明。规划不再生成一套计算结果 ID 和依赖符号图。`facts` 保留访问材料所需的来源事实和未确定的业务含义，不复制完整 Schema，也不重复登记尚未执行的计算结果。
- `decision_conditions` 保存需要研究的比较或建议、`basis`、`criterion` 与实际出处。这里说明要回答的判断问题及已有依据；可执行输入、条件及随结果变化的表达在正式程序中定义一次。数学比较依据为 `mathematical`；透明的事实推导可记为 `analytical_derivation`，它本身不构成业务评价标准；业务判据按用户、规则或 Schema 的真实来源保留，尚缺依据则为 `unresolved`。只描述事实时可以为 `[]`，不要求在读取和计算之前预写真假分支或候选结论。
- 不确定项按 `schema`、`probe`、`business_clarification` 区分。字段定义尚未展开时，可先读取当前来源的精确 Schema；真实取值和查询覆盖需要后续 Probe；只有无法由规则、Schema 和 Probe 判定且会实质改变答案的业务定义才交给用户澄清。
- 已选数据源 Schema 中的字段含义与关系是输入依据，不是已经确定的计算公式。语义计划不得重新选源，也不能将没有依据的代理口径写为已确认规则。

## 计算到洞察表达的承接

计划保存解释对象、比较总体、真实依据和需要补充的业务信息；有输入与有评价依据是不同信息。执行阶段从实际计算结果定义判断并求值，表达消费这份结果，不再翻译一份预写的自然语言条件及结论分支。事实描述与业务判读都可以形成有价值的洞察，表达深度由问题及已有依据决定。

`basis` 表示解释结论的依据，而不是条件是否能够用数学计算：相等、大小关系、并列、实际差额等可由数学关系直接确定；业务评价则取决于提供的业务判据。用户要求、会话规则和 Schema 中的判据按其真实来源承接；仅有数值字段、状态枚举或可计算的百分比，不等于已有风险、健康、效率或充分性的评价标准。没有这类依据时，用事实描述及判断边界承接，而不是先指定一个阈值。

## 交给实现的结果定义

筛选和分类的业务要求随原始依据保留。`definition` 记录用户或规则指定的成员范围、业务含义和未确定项，已有公式保留原义；具体筛选、聚合与转换实现统一在正式执行定义中产生。探索性的展示分组说明用途，业务分类承接实际规则。无法确定成员范围时保留未确定项，已确认的原始分布仍可分析。

同一分组结果中的数量、占比、总量和均值是不同的业务量。`result_fields` 保存所需业务量的含义与单位；规划阶段不再生成逐字段算法或分组符号图。用户已经提供的公式仍作为原始需求保留。正式程序定义实际输入、算法、结果表及判断。

每条计算需求说明一个实际业务量或相关业务量的范围；依赖已有计算结果时，正式执行定义直接引用它，不在规划中另建一套结果目录。

`criterion` 记录已有判据及出处，或需要研究的数学关系；可执行条件属于正式程序。缺少业务判据时保留事实比较与解释边界，不用自定阈值补出评价标准。事实描述同样可以说明分布差异、变化来源和需要补充的业务信息。

业务判据用 `source_references` 保留实际来源定位与原文。字段、单位或枚举说明与业务评价算法是不同信息；引用应承载实际适用的规则。`basis` 是本次分析声明的来源类别，不是后端确认了评价正确。纯数学大小、相等、差额和并列不需要外部判据；探索性选择的展示分界可以透明说明用途，但不自动成为业务标准。

这一步保存来源、业务需求和解释依据；正式执行阶段负责唯一算法及判断定义，不从指标名称或报告标题猜测评价标准。新的分析发现仍可在同一语义计划中补充，不能预设计算结果来写结论。

这份 JSON 对象贯穿后续材料计划、Probe 和代码实现；它是可修订的分析语义，不是数据已存在、计算已正确或报告结论已成立的证明。新观察若改变事实绑定或口径，应更新同一份对象；材料计划只决定需要读取和验证哪些来源、字段和关系，不重新发明分析目标。
