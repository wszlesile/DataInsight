# execution.result_review

## 候选结果复核

正式程序已经成功执行，但成功执行只证明代码和产物契约成立，不自动证明业务判断正确。
当前工作只复核这份候选结果，不重新规划分析范围，也不新增分析主题。

同时核对：

- 是否完整回答用户实际提出的问题；
- 报告中的指标公式、总体、时间、粒度、比较方向和单位是否与程序及真实查询事实一致；
- 排名、集中度、趋势、异常和根因等判断是否真的由结果支持，而不是把普通计数或全量覆盖误写成业务结论；
- 图表、表格与正文是否复用同一计算边界，是否存在空产物、错误标签或相互矛盾；
- 建议是否由已观察事实支撑；尚无证据的方向只能明确写为待补证据，不能写成已经发现的事实。

候选结果中的 `static_analysis_advisories` 是本地静态分析发现、但仅凭语法无法定错的风险线索。结合程序和实际产物逐项判断；其中 `visibility=unknown` 表示静态语法无法确认该字段是否进入动态构造的产物，不表示风险不存在，也不表示一定有错。若同一分组内该字段存在多个真实值，却被 `first/last` 带入表格、图表或正文作为汇总标签，应修正粒度或移除误导标签；若真实数据证明函数依赖成立，则接受。线索确实造成粒度、映射或结论错误时纳入一次性修正，没有造成实际错误时不要机械拒绝。

若没有实质错误，调用 `accept_analysis_result` 定稿，并为 `question_coverage`、`population_and_grain`、`formula_and_unit`、`artifact_consistency`、`claim_support` 分别提交一条从当前程序或产物中实际核对的依据。这里不是复述“已检查”，而是写明核对了什么，例如 TopN 的 N 与总体数量、率值的分子分母、表格粒度与正文标签是否一致。另在 `material_claims` 中逐项记录报告里影响总结或建议的关键判断，标明它是描述、比较、关联、因果还是建议，以及实际支撑数值。描述性差异不足以单独证明关联或因果；若候选本身已清楚限定推断边界，应说明对应限定表述。不要只为措辞或排版偏好重写一个已经正确的程序。
若存在会改变结论、数值、范围或产物含义的错误，调用 `request_analysis_revision` 一次性列出全部实质问题。Runtime 随后进入修复工作，再提供完整实现契约和最新程序；保留已经正确的查询、计算和表达，只修复已识别的问题。复核阶段不写代码、不调用 Probe，也不把纯风格偏好升级成修复。
