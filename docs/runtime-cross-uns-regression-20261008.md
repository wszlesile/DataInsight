## 独立来源核对

1. 设备类型表五组数量与占比共 10 项独立查询比较一致；三个源查询行数为 16、15、45，
   与保存快照一致。前两类设备合计实际是 **81.25%**，报告却绑定第一类的 **62.5%**。
   最新状态查询没有截至时点限制，包含复跑开始之后的事件。
2. 质量按检测时间纳入为 OOS **11**、近限 **41**；按批次开始时间纳入为 **10 / 38**。
   当前报告未明确承接两者的业务差异。月份窗口还包含复跑开始之后的 **25** 条检测记录。
   根因优先级把“关联物料批次”这种正常存在，与故障、报警、复检混作排序依据；
   用户要求的包装候选没有进入该排序。
3. `test02` 的真实来源可通过权威已挂载库 `uns_rds` 查询：**33,142 行**，字段
   **timeStamp / value / _id**。直接全量读取触发环境 10,000 行上限，诊断改用全量 COUNT
   和明确的五行 Schema 样本；没有拿样本充当正式分析总体。会话却报告 **76,872 行**、
   11 个 MES 批次字段，并宣称该 MES 表就是 test02 的物理映射。这是在真实目标可用时
   仍发生的来源漂移，不是无数据环境的合理退化。
4. 1 类与 3 类节点通过当前公开 Runtime 查询帮助函数执行真实时序 SQL，均报
   `Failed to find attached database "uns_timescale"`。FedQuery 当前已挂载库清单确实没有
   `uns_timescale`，但时序容器本身在运行。这两类的原生数据验收受环境阻塞。
5. 引用节点权威 `refer_data_type=2`、目标设备表 Schema 为 key/name。当前普通访问地址
   报元数据扫描错误；按已挂载库限定后确认目标设备表不存在。Runtime 不应以另一张
   MES 表的空过滤结果宣称该引用节点无数据。引用用例原问题要求时序趋势，与真实静态
   Schema 不兼容；正确边界说明或必要澄清是合理结果，替换来源不是。
6. 当前 UNS 清单没有历史现金流来源。最终文本没有虚构财务数字，但上游“至少一个
   支持来源”的结构要求把空选择重试成了无关生产工单，随后出现多次无效继续生成。
   财务类当前只能验收不可分析说明，不能宣称完成了财务分析回归。

## 设计层面的结论与后续顺序

### 1. 首先修来源范围与实际访问身份的传递

用户选择的 UNS 实体、引用目标、来源查询契约和原始 Schema 必须作为权威身份贯穿
Preparation、语义规划、物料规划、查询与报告。语义检索候选不能被误当成该节点的
物理映射；目录路径也不能自动成为业务字段过滤条件。当前的最早问题出现在来源选择
及其下游规划边界，Evidence 只是在为错误来源的真实计算提供引用。

要同时处理原生关系源的库限定身份，以及时序源的环境可用性与明确不可用状态。
不能用召回的其他表覆盖失败来源，也不能对所有问题一律要求用户澄清。

### 2. 再完善事实口径与展示消费的身份

计算结果需要携带明确的总体、时间角色、粒度、单位、比较对象，以及展示选择所需的
完整结果身份。报告应消费这些已有计算结果和比较事实；仅有 result/field/row 引用可解析，
仍可能选到错误值。不能把 Evidence complete 当成业务正确，也不能加入自然语言
语义判定重试。当前质量排序与时序解释问题需要分析 LLM 在正确规划上下文中解决。

### 3. 补齐产物的通用消费传播，并减少多源阶段的重复上下文

任意 Python 能力继续保留。合法的派生视图、表格和图表需要通用地保留实际来源与
计算边界，不能按个别会话语法打补丁。partial 状态应诚实保留直到这些边界有真实记录。
性能要处理完整多源知识的存取方式、工作阶段责任和无进展状态的退出；不能删来源、
删分析维度、提高测试长度上限或降低报告深度换取通过。
