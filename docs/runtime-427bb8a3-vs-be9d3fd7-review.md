## 2. 不变目标

新增需求必须保留：同轮次澄清，以及不要求调用方创建空间/会话的外部分析接口。

Runtime 优化服务于准确性、稳定性、报告表达力和总耗时；不得用缩减分析范围、限制洞察表达、放弃证据链或删减必要信息换取通过。查询、指标、图表、表格和报告继续在一个洞察语义中形成完整 Python 程序。准备阶段不是指标或报告规划的硬约束来源。

需要分别证明“新增需求完整”“原功能未回退”“设计带来收益”，三者不能互相替代。

## 3. 当前实际架构

### 3.1 新增需求

- `invocation_policy.py` 定义交互/外部调用策略、澄清模式和输出合同。
- 同轮次澄清有 Runtime 工具、任务等待状态、回答接口、恢复请求、SSE 和前端交互实现，支持多项回答。
- `workflow_insight_controller.py` / `workflow_insight_job_service.py` 提供创建、查询、取消接口，使用内部空间/会话承载，转换 UNS 范围，并传入分析偏好。
- 外部调用关闭澄清和 Evidence，支持 standard/text/json 输出；JSON 支持有限的 Schema 关键字集合，不是完整 JSON Schema 实现。

以上表示实现链路已存在，不代表所有边界已验收。

### 3.2 Runtime 设计调整

1. `runtime_prompt_loader.py` 将语义内核、必需规范和资料目录组合成上下文。
2. `runtime_contract_registry.py` 依据实际数据源能力并集、输出类型、澄清模式和追问状态选择必需包。混合源不是二选一。
3. 必需包在第一次请求中已经注入；`read_runtime_reference` 是可选的完整说明/示例查询。
4. Agent 暴露 `probe_analysis_data`、`submit_analysis_program`、资料工具和可选澄清工具。前两个仍调用共同的 `execute_python.func`，但模型看到的工具协议已变化。
5. 正式程序仍是一次独立闭环执行，不共享前一次 Python 的变量/DataFrame。
6. 外层恢复通过 `prior_messages` 与消息合并延续 ReAct，而不是每轮重建全新的对话。
7. 新增组合查询 helper、源码定位/补丁修复、执行反馈及静态检查；Evidence 也有独立改动。

**判断：当前不是“只多一个分析计划，然后按计划加载原 Prompt”。它没有模型维护的资料加载计划，而是后端自动选包、模型可选查资料的 ReAct。也不能把本次已经撤销的强制 plan 工具当成当前实现。**

## 4. 设计取舍

| 变化 | 设计价值 | 尚需证明的部分 |
| --- | --- | --- |
| 结果/交互策略独立 | 新需求不必改变所有调用场景 | 所有入口、恢复和取消是否一致 |
| 数据源能力并集选包 | 避免加载不适用的方言，保留混合查询 | 识别异常/未知引擎时是否完整供给 |

| 当前 ReAct 连续修复 | 保留代码与工具反馈，避免修复失忆 | 多次修复仍累积消息，不能宣称已实现动态工作记忆 |
| 组合查询 helper | 将重复机械步骤集中在本地 | 旧 loader 路径和多源/文件/时序行为是否等价 |

## 5. 已确认问题与限制

### 5.1 澄清回答存在双重事实风险

`AnalysisTaskService.resume_from_clarification` 中，选项与自由文本同时提交时，`answer_text` 可来自用户文本，而 `resolved_value` 仍来自选项。两者冲突时，下游拿到不一致的用户事实。

同时，答案列表按 item_id 转字典会覆盖重复项；单项待答时允许回退使用首个提交项。需要明确请求匹配规则，而不是交给 Runtime 猜测。

### 5.2 澄清恢复不是完整 ReAct 恢复

`_build_clarification_resume_context` 保存 Preparation、context_mode 和 Probe 观察。恢复时重新组装输入，并补用户答案；没有持久化完整工具调用消息。因此不能声称暂停/恢复前后是字节级连续的同一 ReAct。是否丢失澄清前的重要分析依据，需要专门验证和确定最小必要恢复状态。

### 5.3 严格 JSON 校验仍有缺口

直接调用 `validate_json_output` 验证 `{'x': float('nan')}`、字段类型 number 且 minimum=0，没有拒绝。下游可能还有序列化防护，但该校验函数自身不足以保证严格 JSON。这是本地实际复现，不是推测。

### 5.4 上下文渐进性有限

`build_prompt_messages` 首次合入完整数据源上下文与适用规范；外层恢复保留消息并继续追加。可选参考资料也以工具结果进入历史。该方案具备按类型供给，不具备完整的工作记忆替换/淘汰机制。没有证据说明长任务的累计上下文一定下降。

### 5.5 Prompt 完整性尚未被充分证明

现有 parity 测试覆盖 helper 名称、关键能力标识和部分示例，但不是 `be9d3fd7` 原文所有规范逐项映射。测试通过不能证明 Python 规范、语义说明和负面约束没有遗漏或改变。后续需原规范条目到当前载体的对应清单，不再凭文件数量判断完整性。

### 5.6 不能把全部静态校验都归因于本次变更

基线本身已有较多静态校验。本次新增了 helper 签名、字段/投影、组合查询约束等检查；应逐个按 diff 识别来源。保留能够证明错误的检查，对推断能力不足导致的拒绝单独举证，不能笼统删除全部检查或一律认定为正向。

## 7. 后续收敛顺序

1. 新需求：先固定澄清/外部接口的验收矩阵，独立确认多项回答、取消、断线恢复、禁用模式、身份隔离、三种输出及不生成 Evidence。

3. Runtime 取舍：将工具形态、组合 helper、静态检查、源码修复、消息承接分开评价。不再将它们作为一个整体实验同时重做。
4. 仅对已证实的缺口提出最小修改，列出可能受影响的入口/行为，再落地。暂不增加强制规划阶段、指标中间对象或报告模板。
5. 最后同环境、同问题、同数据源分别跑简单及混合/复杂场景，对比正确性、表达力、首次成功率、修复次数、总耗时和请求/累计 token。出现问题按设计/契约/实现/环境分类。

## 10. 可以明确区分的正向修正

### 10.1 无数据不能由次数证明

基线 `_apply_probe_no_data_retry_limit` 达到上限后要求直接切正式分析，以无数据或不可分析收口；执行上下文也曾用次数决定 confirmed_no_data_result。

当前改为读取真实执行的零行 QuerySnapshot；计数只针对当前任务中的真实 no_data 信号，正常 Probe 不计入，达到次数不作为无数据证据。新查询有数据/失败时不应复活旧空集。这个方向比单纯次数判定更合理，不能为回退工具名称而撤掉。

### 10.2 修复范围保护以真实执行为依据

当前 `_validate_scope_preserving_technical_repair` 增加 previous_scope_is_proven，缺乏成功物理访问证明时不强制继承。这降低了错误代码声明永久锁住分析范围的风险。仍需检查它是否覆盖所有合理删减场景，不能把“方向正确”直接等同于没有误伤。

### 10.3 实际函数签名和必要规范并集

从真实执行命名空间生成 helper 签名，以及按混合源能力并集注入必需规范，都是可单独保留的机械一致性改进。它们不需要新增强制规划节点。

## 11. 收敛判断与执行边界

当前适合做有限收敛，不宜再整体重构。建议按以下独立批次讨论/落地：

1. **交付完整性**：澄清开关与各入口、答案一致性、恢复计时/派发失败、严格 JSON。只改新需求链路，单独测试。
2. **能力等价**：处理确认的图表表达收紧，以及原规范与当前 API 不一致项。不重新设计指标或报告对象。
3. **Runtime 收敛**：保留完整语义、真实查询事实、连续 ReAct、能力并集和签名一致性；对工具拆分、implicit Probe、patch 与 AST 新检查分别给出收益/误伤证据，再决定保留或回调。
4. **真实验收**：先简单场景确认完整路径，再混合源和复杂场景；新增需求功能验收与模型效果验收分开记录。

没有证据前，不应宣告全部新增静态检查是负向，也不应宣告全部实验机制是正向。现阶段确定的问题已足以制定边界清楚的修正清单，无须先继续真实回归去随机碰问题。

## 13. 首批交付缺口修正（未提交）

本节记录后续落地状态，不修改前文的审视基准：

- 已增加前端澄清开关，新建与异步刷新传递同一 clarification_mode。
- 单项文本澄清可由主输入框提交到同一任务；多项/仅选项仍在对应澄清区域回答，避免猜测文本对应哪一问题。

- 本批未改 Runtime Agent 工具、Prompt、ReAct 消息、Probe/no_data、Evidence 或计算校验；图表收紧和恢复记忆边界仍待独立处理。

## 14. 第二批确定缺口修正（未提交）

- 图表执行层原本仍支持 helper 未覆盖类型的原始 chart_spec，现将 result.artifacts 和通用图表修复提示对齐这一边界。未放宽已有图表数据校验，也没有要求所有图表改用原始结构。
- 澄清挂起时，将当前真实 ReAct 消息序列持久化到私有 resume context；恢复后沿用该序列并追加用户回答，不重建 Schema、不再重复注入 Probe 摘要。
