## 3. 按来源区分问题

### 3.1 待提交引入，已明确纠正

**参数读取越权改变查询值。**

`tools.get_analysis_parameters()` 原本只合并 defaults 与本地重跑 overrides。待提交实现根据全局时间上下文，把任意嵌套字典中的日期 start/end 转成 `Asia/Shanghai` 时间戳。它并不知道字段是自然日、字符串、无时区时间还是绝对时刻，也不知道后端数据库的转换语义。

r11 的模型代码默认值仍是 `2026-08-31`；不是模型先改了日期。这个后端转换是确定的负向改动。本轮恢复原值合并，覆盖值也保留原类型与原边界。不在参数读取层做隐式时区转换。

**一次 Probe 后撤销工具能力。**

待提交 `_runtime_probe_enabled()` 在收到一次 `probe_feedback` 后从 Agent 工具集移除 Probe，并断言已有反馈就是完整探测事实。它把调用次数误当成知识完备性，正式查询遇到新格式、路径或空集问题时无法再核实。

本轮移除这个开关及按 Probe 开关拆分的 Agent 缓存。Probe 与正式提交始终属于同一 Runtime 能力；用户澄清是否启用仍由 invocation policy 控制。没有调整总轮数、请求超时或传输方式。

**修复协议给出冲突指令。**

工具反馈提供 `repair_target`，通用指令却要求“重新生成完整代码，不要只修改局部片段”。本轮把通用修复说明对齐到已有协议：改动完整落在允许范围内可 patch，否则提交完整代码。仍重新解析、执行合成后的完整程序。

### 3.2 基线已有，当前改造没有彻底解决

**失败记忆缺少任务隔离。**

- `_build_turn_failure_memory()` 按 `turn_id` 读取失败记录，没有限定 `analysis_task_id`，也没有排除当前执行之后的记录。
- `_count_probe_no_data_failures()` 同样按 turn 汇总，重复刷新可能把之前任务的结果计入本次预算。
- `_load_confirmed_no_data_query_snapshots()` 使用 turn.started_at，而其他路径使用 task ID。不同读取入口对“本次分析”的定义不一致。
- invoker 的当前 ReAct 执行加载已经按任务隔离，但 tools 的失败记忆仍按轮次加载，形成两套不一致的状态来源。

代码已确认该风险；本轮没有在断开的数据库上重新量化 r11 究竟继承了多少条旧失败，不能把风险写成已测得的实际条数。

**正常观察、空集与失败混为一类。**

`PROBE_NO_DATA_RETRY_TYPES` 包含 `probe_feedback`。Probe 成功返回真实观察也以 retry/failed 形态持久化，参与 no-data 计数；达到次数后生成“以无数据结论收口”的指令，并影响 `confirmed_no_data_result`。调用次数不能证明业务范围无数据，尤其多查询中有成功、有空集、有不可用路径时。

不能只把 Probe 从计数集合删除：还需要完整承接真实空集的确认、部分无数据披露与最终无数据报告，否则又会丢失基线能力。

**部分语义检查仍把“无法证明”当“已经证伪”。**

复现最小例：

```python
frame = load_data_with_sql("SELECT MAX(amount) AS amount FROM sales")
report = f"Highest amount: {frame.iloc[0]['amount']}"
```

SQL 已计算唯一最大值，`_validate_report_extrema_selection_contract()` 在基线与当前都会拒绝。对 `ORDER BY amount DESC` 的合法写法，基线拒绝，当前接受，说明待提交的三态改进有价值，但不完整。

配对指标/括号、时间窗、最高最低等检查仍包含对 Python 文本常量和格式的解释。不能因为分析经过 AST 就声称它是确定性业务校验；字段不同也不自动证明总体不同。

**恢复备用路径仍不完全符合当前调用策略。**

连续 ReAct 主路径已使用短恢复指令，但 `_build_analysis_recovery_instruction()` 仍保留单候选强制精确筛选、“不要再次询问用户”、必须图表报告等旧要求。它与允许澄清以及 text/json 调用不完全一致。它是否影响每次执行要看实际入口，不能把备用路径风险声称为 r11 的直接原因。

### 3.3 正向推进，但还需要行为验收

| 改动 | 应保留的价值 | 尚不能宣称完成的部分 |
| --- | --- | --- |
| 同一 ReAct 保存 AI/tool 消息 | 修复继承原代码与确切反馈，不重建一份失真的摘要 | 数据库恢复与任务隔离也要一致 |
| Prompt 内核 + 能力包 | 按完整选源类型取并集，混合查询不会只装一种方言 | 文本存在不等于模型能稳定使用 |
| 完整 Schema 去重表示 | 去掉空 example 和重复字段索引，不按长度删字段 | 上游 Schema 对业务含义的描述仍可能不足 |
| 组合查询 helper | 统一校验、快照注册、执行的机械顺序 | SQL 与约束的双重表达仍需减少错位 |
| 按真实签名检查 helper | 能精确反馈错误参数 | 不应把未知动态表达式当成错误 |
| 源码范围修复 | 局部问题无需重新生成整个报告 | 范围不够时必须允许完整修复 |
| 同轮次澄清 | 保留用户原始补充，在同一任务内恢复 | 应有真正歧义与无需澄清的对照用例 |
| 外部 text/json API | 独立输出契约、关闭澄清与 Evidence | 不能让交互报告的恢复指令污染该通道 |
| 后置 Evidence | 正式代码继续不承担 Evidence 创作 | r11 的 apply/排序计算边界仍 unresolved |

## 4. Prompt 架构判断

当前不是新的语义规划 Stage，也不是按指标模板写报告。模型仍生成完整 Python，包含查询、计算、图表、表格与动态报告。

实测纯协议文本，不含 Schema、对话和工具消息：基线 86,358 字符；当前关系型 22,052，时序 24,532，关系+时序 27,396，关系+时序+文件 29,033。r11 首轮模型实际输入约 24,235 token，正式提交前约 27,847 token。减小输入是事实，但它不能单独证明语义理解提高。

当前装配是“按相关能力选择后一次全部注入”，不是执行途中按需检索文档。因此它解决了无关方言常驻和重复说明，没有彻底解决相关能力持续增长的上限。文档不能把它表述为已实现渐进加载或已达到最优。

优先解决状态与 API 一致性，再决定是否需要延迟加载少见机械文档。用户问题、完整 Schema、业务规则、澄清答案、当前任务观察不属于可裁剪文档；混合源按所有选源取能力并集。不得通过更窄选源、截断 Schema 或省略方言换取更小 Prompt。

能力对齐测试目前主要证明 API 名称、方言标记、装配组合及示例语法存在，不能证明原有分析能力和表达力不回退。此次日期测试曾要求错误的自动时区转换，说明测试本身也必须从不变量出发，不能只复述实现。

## 5. 与成熟 Agent 实践的对照

参考官方资料，不据此声称存在适合所有模型的唯一最优架构：

- [Function calling](https://developers.openai.com/api/docs/guides/function-calling)：清晰参数与输出定义、减少模型填写已知信息、组合固定顺序的操作、通过评测选择工具规模。当前组合查询 helper 符合这一方向，隐式改写参数不符合最小意外原则。
- [Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)：保留连续交互状态。当前完整 ReAct transcript 是正向改动，turn/task 两套记忆口径仍需统一。
- [Evaluate agent workflows](https://developers.openai.com/api/docs/guides/agent-evals)：先检查端到端 trace，再建立可重复数据集比较。单次执行成功、单纯 Prompt 字数下降和 API 名称齐全都不是结果质量验收。

基于本项目的判断：差距主要是同一事实在 API、状态、校验、反馈中的表示不一致，不是缺少另一个 Agent/Stage。模型也可能犯错，但在确定性后端回归和误报未清除前，不能把错误率归因于模型能力，也不能承诺所有问题必然一次成功。

## 6. 后续实施顺序

1. **已做：移除明确的负向增量。** 参数保真、Probe 能力持续可用、通用 patch 指令一致；保留其他未提交功能。
2. **下一步：统一任务观察状态。** 所有失败历史与查询观察显式限定当前 task；澄清恢复沿用任务状态。观察成功、真实空集、执行失败分别记录，按 query_key/真实口径关联，不以 turn 级次数推导全局无数据。保持同一 ReAct，不添加 LLM 调用。
3. **随后：统一反馈与校验证明边界。** 结构错误/API 错误/明确范围冲突可阻断；未知语法和业务解释不直接证伪。主路径与恢复路径消费同一结构反馈，按 output/clarification policy 生成动作，不追加第二份相反业务要求。保留诊断能力，不通过删除检查或新增指标 DSL 来规避问题。
4. **行为级能力矩阵。** 以固定输入验证参数保真、Probe 后新问题、无数据/部分数据、刷新隔离、澄清恢复、SQL/文件/时序/混合查询、标准/text/json 输出，以及等价 Python 写法。正例与反例必须成对，不能只有“该拒绝”的样本。
5. **再进行在线 A/B。** 固定选源/Schema/问题/模型与数据时间，先 Runtime 对照，后完整 Preparation；同一问题重复执行检查稳定性。恢复空间 15 顺序回归，保留 43/44/45/46/47/48 的既有问题记录，不把本轮 48 的修复当成整个空间通过。

每一步完成后检查整条链路，不通过增加固定章节、禁止合法 Python 写法、关闭 Probe 或减少分析范围获得表面通过。复跑必须包含指标独立核算、报告实质内容与业务覆盖、所有结构化数值 Evidence，以及耗时拆分。

## 8. 已确认 Runtime 缺陷修复

本次仅修复既有审计确认的执行、记忆和反馈错位，不开始新 Runtime 架构设计。不修改 Preparation 的职责、选源范围、正式分析的语义所有权、后置 Evidence，也不增加模型调用或重试轮数。

### 8.1 任务历史与观察

- tools 的失败记忆、时间范围保护、修复范围检查、无数据计数和空集事实继承统一以当前 execution 的 analysis_task_id 为边界，并排除未来执行和已删除记录。没有当前 execution 不猜测所属任务；无 task 的同步执行仅读取本次 started_at 之后的无 task 记录。
- 正常 probe_feedback 不再进入失败记忆或 no-data 计数。模型 ToolMessage 使用 status=observation、feedback_kind=observation，保留本次查询快照；前端进度使用 info，不再提示代码重试。数据库 execution 的既有非终态记录方式未新增状态或迁移，不将 Probe 记录标为正式产物 success。
- 内存反馈按 task/执行编号去重；no-data 计数消费工具返回的实际计数，不再另建一个按消息数累加的判断。

### 8.2 无数据收口

- 重试次数只作为预算诊断，不能生成“全部无数据”的事实，也不强迫关闭 Probe、删除来源或固定返回表格。
- 允许无数据说明的依据改为本次任务最近实际观察到的空查询事实，不必耗尽错误次数。最新观察包含有数据、执行失败或缺少实际执行证明时，不能恢复旧空集作为整个结果的依据。
- 在执行查询前出现的语法/API 错误不会抹掉之前有效观察；真实新查询会重新决定事实是否适用。全部空查询记录完整保留，不再截断成 12 条。
- 这是允许模型依据已观察事实生成原因与建议，不是后端证明所有业务路径已经覆盖，更不是自动确认业务解释正确。部分数据仍可正常分析，未知口径仍可 Probe 或按调用模式澄清。

### 8.3 恢复反馈

- 移除备用恢复路径的候选自动定稿、单个精确筛选、禁止询问用户和必须生成图表报告等第二套指令。
- 恢复沿用同一 ReAct 指引，读取实际工具诊断、源码修复范围以及当前 standard/text/json 和 clarification_mode。结构化反馈中的有效诊断、修复说明不再按字符串总长截断。
- 通用反馈不再以技术错误为理由要求删除可选分析内容；Probe 说明不再把未探测来源当作不可分析来源。

### 8.4 静态校验的证明边界

- 极值 SQL 检查使用已有 sqlglot 解析顶层聚合/排序，而不是用 ORDER BY 文本搜索推断子查询或外层排序；组合查询 API 的位置参数按真实签名读取。
- 单行 SQL 聚合不再因没有 ORDER BY 被拒绝。明确相反的排序方向仍阻断；未知排序、动态方向和不支持的表达式保留 unknown 诊断，不推导成确定错误。
- 成对百分比与数量使用不同筛选字段，只能证明实现不同，不能证明业务群体不等价。保留计算依赖诊断，改为非阻断提示；不宣布该指标已校验正确。
- 非阻断诊断写入本地审计日志；同时存在真实阻断错误时，附在该次修复 diagnostics.unproven_advisories 中，不为提示单独增加模型调用。

### 8.5 验证与剩余边界

- 本轮合并执行 16 个相关测试文件，437 项通过；Python 编译检查与 git diff --check 通过。未每次修改都运行全项目测试。
- 定向验证覆盖任务隔离、无 task 入口、重复工具消息、真实空集/部分数据/失败路径、超过 12 条空查询、Probe 后技术修复、恢复的输出和澄清策略、合法聚合/错误排序/未知排序、Prompt 和本地重跑参数能力。

替代正式查询、最终计算或产物。这个边界需要通过跨用例对照确认后再调整，不针对 OOS 增加特例。

5. 每个版本分别审阅首次正式程序和修复后程序，记录范围、粒度、时间、公式和结论变化。

### 12.1 撤销不可靠的成功后阻断审核

试验中的 LLM 一致性审核曾把“计算匹配、无需修改”标记为 contradiction，也把并列最多、
未补充背景说明当作必须重试的错误。增加分类字段未消除误报，反而引出新的修复错误。
因此已删除该审核服务、开关、执行接入和对应试验测试，不把第二个模型的判断当成强契约。
这不是声明准确性已经解决；真实核算及内容审阅仍是回归验收必需项。

### 12.2 已修正的确定性边界

1. 专用 `probe_analysis_data` 已知调用目的，成功查询及打印摘要可自动组成 observation，
   不再为了重复填写 `request_retry` 产生一次模型调用。显式自定义反馈仍支持；通用
   `execute_python` 的旧 Probe 信封要求和正式分析产物要求不变。观察成功不等于无数据。
2. Probe 给模型的反馈保留实际查询口径、执行状态、行数和列等事实；完整 QuerySnapshot
   仍持久化，只移除消息中重复的 SQL/投影元信息，不裁剪 Schema 或改写正式查询。
3. r15 的缺列错误是 `q2_detail`，旧反馈却收集了全程序同名列的 17 个区间，且漏掉其查询构造。
   当前按失败对象及词法作用域给出构造、重赋值和使用位置，不据此做新的静态阻断。
   使用真实 execution 7 回放，源码上下文从 53,714 字符降至 4,925 字符，保留 3 个相关区间，
   每个区间都与原始执行源码逐行核对一致。此量化不是端到端性能提升的替代证明。
4. 补丁输入失败时保留原 `base_execution_id`、源码 hash、原版本行号、继承数据源范围；
   同时报告范围元数据和补丁语法问题。候选代码行号单独标记，不冒充原版本行号。
   不创建执行、不运行有语法错误的代码、不静默接受数据源范围变化。
5. 基线和当前都用 `'本周' in text` 把“本周期”误解析为本周，r15 因此被错误地要求改回本周。
   修正时间词边界及缓存版本。“本周期/上周期/过去若干周期”不再被本地设为日历周；
   明确的本周、上周、近若干周保持原能力。未明确的业务周期交给 Runtime 依据上下文判断，
   必要时按调用策略澄清，不由校验器杜撰。

### 12.3 仍待验收的事项

  有完整 Schema、执行通过、Evidence complete 均不能证明这些语义正确。

- 395 项相关测试通过，覆盖修复、时间、Probe、澄清、输出模式与 Prompt 能力承接。

### 12.4 r16 独立核算与 Probe 返回类型审视

r16 在“本周期”没有明确日历范围的情况下采用最近完整月（2026-08-01 至 2026-09-01），
正式代码一次执行成功约 16.8 秒，首次正式结果到达约 174.8 秒，后置处理约 40.5 秒。
这和 r15 被本地误锁为本周的工作量不同，不能直接用两者总时长之差宣称净性能提升。

独立 SQL 核算确认生产批次 744、OOS 批次 21、近限批次 168、近限检测 181。
但报告“最严重偏离”不正确：低侧偏离最大为 11.7535%，代码以带正负号的比值排序，
选出高侧 11.3667%。同时，代码把通用 `nonconformance_count>0` 命名为包装因素，
把物料关联数至少 2 个命名为物料风险，不能据此支持根因优先级。
这些缺陷存在于首份正式代码，不能归因于修复丢失原报告。

Evidence 编译状态 complete，候选绑定 86/86，结构化槽 41/41，共 55 个定义。
这说明产物位置有覆盖，不代表上述算法与业务含义正确；未据此回写远端或宣布验收。

两次失败 Probe 原因均为查询超过 10,000 行。未提交的 `ProbeQueryOutcome` 对失败结果
隐式提供空 DataFrame，统计 helper 随后报缺列，掩盖原查询失败。同时它只部分模拟 DataFrame，
`len(outcome)` 仍是字典键数。现已撤销这个混合返回类型的便利行为：

- 外层保持查询状态信封，`data` 才是 DataFrame；支持属性访问状态字段，不再转发任意 DataFrame 方法。
- 查询失败 `row_count=None`，空集仍为 0；真实查询失败不再被转换成成功空表。
- 统计 helper 可显式读取成功信封内数据；读取失败信封时传播原始错误类型与消息。
- 这不是增加失败重试或自动 LIMIT，也没有缩减 Probe、多源查询和正式分析能力。
- 最新 477 项相关测试通过，包括工作流接口和同轮次澄清。此最后一项调整完成于 r16 之后，
  有成功、空集、失败、多种统计 helper 及复制协议的离线测试，尚未新发起完整模型复跑。

本轮的确定修复与未达标的语义问题已分开记录；不通过新增 LLM 审核器、统一报告模板或
字段名称特判来把本次样例改成“通过”。后续需要验证首份正式代码如何保留业务含义，
而不是再以完整 Schema、首轮执行成功、Evidence complete 作为准确性的充分条件。
