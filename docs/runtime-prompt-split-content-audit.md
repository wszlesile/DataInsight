## 已处理及需要区分的变化

- 自定义 chart_spec：原文允许 helper 无法表达时退回；当前工作区已恢复相同例外，执行层本就保留该能力。
- 原文“所有加载函数都返回 DataFrame”本身与低内存迭代器冲突；当前逐 helper 标明返回值是正向修正，不应逐字恢复错误总述。
- execution_intent 与 request_retry：当前 Probe/正式工具会绑定用途，Probe 可自动反馈。这是设计变化，不属于文字遗漏；应单独验证，不在内容审计中直接撤回。
- 组合 query helper：校验/注册/加载集中是当前 API 变化，原底层 validate+loader 仍可用。旧模板不能不经替换直接搬入。
- JSON/text 不生成标准图表：符合新增需求，不是丢失图表能力。但计算准确性原则仍须共用。
- 原文“默认考虑 1..3 张图”已改为按实际问题产生有职责的图表。这是展示偏好的改变，不宜当作必须恢复的硬数量要求；需评估多视角表达，而非用图数验收。
- 元数据类型到 pandas dtype 的机械对应被简化，不宜盲目恢复为绝对要求。实际 SQL 返回类型可能不同，应先观察并按字段含义处理。

## 示例与按需加载

1. query.local_file 和 query.relational 的完整示例仍在文件中，loader 用 omit 标记从首次注入移除；read_runtime_reference 可返回完整示例。属于延后供给，不算删除。
2. 原版完整示例不是全部逐字保留；当前示例已围绕组合 helper 重写。需要按“完成查询、计算、判断、图表、表格、保存的示范能力”核对，而非恢复旧字段和旧 API。
3. 当前文件示例的业务建议是固定字符串：“建议结合头部类别的明细构成和后续变化判断其贡献是否可持续。”它并不由实际条件分支选择，与内核“不用通用建议补章节”不一致。是示范质量问题，不是候选会话特例。
4. 核心包自动加载；同类多个数据源不会触发 query.cross_source，只有不同能力类型组合才触发。通用多源业务规范不能只放 cross_source 包。
5. context.followup 只在 followup 模式注入。通用“历史对话讲用户说过什么、结构记忆讲执行做到哪”的边界不宜只依赖追问分类；当前 context.analysis 有概要但不包含原来完整说明。

## 契约目录组织

契约 ID 不变，物理文件按模块归档：

```text
contracts/
  context/       analysis.md, followup.md
  execution/     core.md
  query/         relational.md, time_series.md, local_file.md,
                 minio_file.md, api.md, cross_source.md
  result/        artifacts.md, text.md, json.md
  interaction/   clarification.md, no_clarification.md
```

registry 保持显式 ID 到文件路径映射，加载条件与参考工具调用方式不变。新增目录与注册表一致性测试，防止文件遗漏、孤立或测试只扫描顶层文件而漏检。

`query.cross_source` 不等于通用多数据源规则。常驻 context.analysis/execution.core 已承接关系可信度、真实访问范围、多路径 Probe 和部分无数据规则；standard 输出中的独立多源图表规则由 result.artifacts 承接。cross_source 保留混合类型专属的原生查询下推、跨源总体/时间/粒度/单位对齐、关系表与 ts_query 联合查询、文件/API 与表的小结果组合说明，删除重复的常驻规则。它仍只在本轮包含多种查询能力时加载，不因同类型来源数量增加而重复加载。
