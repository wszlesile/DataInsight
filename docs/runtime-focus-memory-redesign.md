# Runtime 聚焦工作与记忆管理复核方案

## 状态与目标

本文是设计复核结果，不是整体已实施或已验收的声明。当前暂停真实扩跑，按
已核实的联合行为缺口逐项修正，不整体重写执行路径。比较基线为 be9d3fd7，
并参考当前分支已提交版本及未提交修改。证据与进度见
[联合行为核验](runtime-focus-memory-joint-audit.md)。

目标：降低模型同时处理业务理解、查询、计算、API、产物规范与历史反馈的
负担，使统一洞察语义下的 Python 程序生成更稳定、更准确，整体效率改善。
报告表达力、数据源能力、Probe/no-data、Evidence、本地执行、洞察任务、
同轮次澄清和外部分析接口均属于保留范围。

状态机、类型化记忆、按需资料都是手段。验收对象是信息是否连续转化、代码
是否正确、报告是否有价值及总成本，不能用模块数、单测数或更小输入替代。

## 本轮推进教训

1. 把材料准备等同于分析进展。understand/select-work/plan 可能只重复
   Preparation，而实现调用仍独立承担大部分分析判断及编码，新增调用没有
   稳定减少后续负担。
2. 状态、记忆、协议分别修改，缺少联合约束。一个模块要求补载 Schema，
   另一个模块隐藏 reader；有局部单测通过，整体行为仍自相矛盾。
3. 材料计划被赋予过强权威。投影函数按计划的 question/fact/relationship IDs
   过滤语义上下文，计划遗漏可能遮蔽分析需要的信息。局部焦点不能变成全局范围。
4. 归档只解决文本长度，没有充分解决知识有效性。旧代码被替换，旧分析文字和
   部分诊断仍保留；事实缺少来源版本、适用范围和明确替代关系。
5. 通过关闭工具减少循环，也可能阻断合法补充路径。不能要求模型必须先提交
   已知缺资料的程序，失败后才获准读取资料或 Probe。
6. 过早从代码现象推出架构结论。顺序回放结构化事件可以是确定性的状态 reducer；
   不能仅因扫描 messages 就认定它天然混乱。内外两层循环也不自动构成根因，
   应验证其状态继承、去重和恢复行为后再决定是否调整。
7. 错读指标会误导优化。重新核对原始文件后，会话 44/64 的采集耗时为
   201.843 秒，SSE done 为 201.703 秒；此前转述的约 2002 秒是读数错误，
   不是采集器故障，也不是模型耗时。数据库报告保存约 197 秒属于另一事件。
   不据此计算退化倍数。当前没有证明优于基线。

## 核心模型：共同推进工作、记忆与上下文

一次工作单元由以下内容共同定义：

```text
当前目标与版本
本次要解决的问题
所需信息及其来源版本
已有判断及其依据
可执行动作
预期产出及下一步依赖
```

流程是：选定有效工作 -> 装载其必要信息 -> 模型判断/工具执行 -> 记录真实
成果 -> 更新受影响的工作 -> 编译下一次上下文。三者在同一工作修订下更新，
不能工具已切换而 Prompt、Schema 和诊断仍来自另一修订。

### 区分生命周期与工作焦点

生命周期只表达 ready/running/waiting/completed/cancelled 等机械状态，
由本地根据真实事件维护。取消与澄清沿用已有产品语义，不重新创造失败路由。

工作焦点表达解决什么：理解某个语义依赖、补充资料、验证查询、实现程序、
修复程序。焦点可往返，不是每个问题都必须遍历的线性 Stage。

模型判断缺什么信息、哪种分析方法适合、是否需要 Probe 或用户澄清；本地
检查动作是否允许、所引用资料是否存在、版本是否过期，并装载对应协议。
本地不宣称仅凭一次 Probe 成功就知道业务语义完整。

相同焦点可以完成多个有信息增量的动作；没有必要单独消耗一轮调用只声明
“下一步做实现”。状态由已有动作结果推进，材料请求可以与简短工作更新一起提交。

### 工作记录不是另一份强制分析对象

保留全局用户问题、业务分析方向、覆盖要求和未解决问题的索引。模型形成的
判断作为可修订笔记：它判断了什么、依据何在、仍有什么疑点、会影响哪部分工作。

不要求事先列齐指标、不预写未知结果的报告、不规定章节模板。分析过程中
自然形成的粒度、公式选择和比较方式应记录并传递，不能为了避免提前规划
而把所有业务判断都排除在工作记忆之外。

小任务在材料充足时直接编程。复杂任务按实际未解决依赖先做必要工作；没有
信息增量的重复计划和重复读取不算进展。

## 工作记忆

保留原始审计记录，另维护当前有效记录的索引。正文优先引用已有权威存储，
不另复制一份巨大的 JSON。每项记录包含类型、身份、版本、来源、适用范围、
依赖与有效性；模型判断与真实执行观察必须可区分。

| 记忆 | 有效性与更新 |
| --- | --- |
| 用户要求和澄清 | 保留完整原文与修订关系，模型不能自行覆盖 |
| Preparation 与 Schema | 保留原始版本及完整信息；局部阅读不减少全局候选范围 |
| 分析判断 | 标为模型判断，记录依据；依据变化时提示复核，不自动当事实 |
| Probe/Query 观察 | 绑定查询、参数、字段和范围；不同范围不互相覆盖 |
| 当前程序 | 指向最新实际完整源码；patch 应关联物化后的版本和执行 |
| 执行诊断 | 活跃错误绑定程序版本；历史错误保留审计，按相关性提供未解决约束 |
| 工具与协议 | 使用同一注册来源、能力与版本，不在多个包手写冲突摘要 |

旧信息不再逐条回放给模型，也不因 token 上限直接删除。无关信息保存在本地，
按明确索引补载。新观察不是旧问题已解决的充分证明，是否替代由身份及适用
范围决定；无法本地确定时保留不确定性。

## 上下文编译

每次调用由同一份工作记录生成：

1. 全局方向：当前用户问题、必要澄清、输出要求、全局覆盖与未解决问题索引。
2. 当前工作：本次要解决的问题、已有判断、最近动作及其真实结果。
3. 必需资料：相关 Schema 原文、业务关系、Probe 观察、当前程序和诊断。
4. 必需协议：按动作、数据源能力和输出模式选择的完整规范及工具。

协议分两层：跨动作必须遵守的少量执行边界常驻；查询语法、图表构造等在
对应工作加载。完整程序实现时，一次提供其所需的全部实现协议，不能只给
目录再让模型猜 API。混合来源使用能力并集。

同一记忆正文只出现一次。原始历史中的探索文字不能自动成为新一轮指令。
局部 Schema 投影必须保留关键描述及关系语义；所需新字段允许即时补载。
全局业务覆盖不能随当前字段焦点过滤。完成 Probe 后有用的真实查询定义
可以复用，不因其是 SQL/源码就一律丢弃，也不无差别回放所有查询。

| 焦点 | 主要输入 | 成果 | 合法补充路径 |
| --- | --- | --- | --- |
| 解决依赖 | 问题、已有判断、相关 Schema/关系 | 有依据的判断或明确未知 | 资料读取、Probe、必要澄清 |
| 查询验证 | 已选口径、精确 Schema、查询/Probe 协议 | 真实观察及适用范围 | 补读资料、修正 Probe |
| 完整程序实现 | 全局方向、有效判断、查询事实、Schema、实现协议 | 一份完整 Python 程序 | 新依赖可补读或 Probe，不必先制造失败 |
| 程序修复 | 当前程序、诊断、相关依据、完整必要协议 | 新程序或有依据的方案修订 | 补读、Probe、必要澄清 |

补载后保持原焦点，消费新信息后继续原工作。只有业务依赖真的变化才修订
计划；不能一补资料就重启整个分析，也不能因一次观察成功强制忽略其余未知。

## 推进顺序与退出条件

1. 完成现状核验：从历史成功/失败请求逐调用还原实际工作、信息来源、工具
   可见性和时间；同时对照 be9d3fd7。区分已确认的协议矛盾、性能相关性、
   尚待证明的因果关系。暂不把必须新建 Driver 作为结论。
2. 定义联合行为表：每类动作对应必需上下文、记录更新、合法后续动作。
   在实现、修复、Probe、澄清恢复、外层续跑上做无 LLM 的事件重放检查。
   缺资料必须能补、旧历史不能改变新决定、混合来源协议不能丢。
3. 先收敛记忆与视图：复用已有存储和 ReAct，把当前有效信息组织成一致视图，
   关闭重复投递与陈旧指令，不同时重写查询、执行、Evidence 或 Preparation。
4. 再收敛动作：移除无增量的强制选状态调用；按联合行为表管理工具和协议。
   模型保留业务判断与合法补充能力。本地状态存储位置按跨调用/澄清恢复需求
   确定，优先复用现有框架能力，不预设替换整个 Agent。
5. 本地请求重放验证：用真实已保存轨迹检查上下文完整性、重复量、来源版本、
   旧程序替代及修复承接。测试必须覆盖实际框架集成，不能只断言工具名列表。
6. 同条件真实对照：先一个简单会话、一个确需 Probe 的会话，再复杂多源。
   同模型/输入/数据/配置，区分 Preparation、模型、执行、Evidence、采集耗时。
   检查数值、判断、报告表达和引用；多次独立运行评估波动，不以一次成功验收。

每步都有可比保存点和独立变更范围。功能迁移与架构优化分别记录验证，不能
因效果不佳整体撤销需求。若新增工作没有减少后续返工或提升正确性，先审查
该工作是否有实际信息增量，不继续添加控制层、重试次数或禁止语句。

## 当前结论

按工作组织信息仍有合理性；当前实现未证明把这件事做好。需要修正的是
动作、信息更新、上下文投影的联合设计。显式状态存储可以是其中一部分，
但它自身不解决业务判断负担，也不能保证模型一次正确。新方案必须先通过
联合行为检查，再由真实对照检验是否产生稳定的正向效果。
