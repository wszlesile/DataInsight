# Runtime 上下文与能力契约设计

2026-09-03 后续设计提案：[分析程序连续构建](runtime-program-construction-design.md)。
提案补充同一 Runtime 内的程序版本、可选工作记录及局部验证，尚未实施；本文仍描述当前代码，
不能把提案中的草稿和检查工具当作当前已具备的能力。

## 1. 目标

正式分析 Runtime 是查询、指标、图表、表格和报告表达的唯一洞察语义所有者。该原则不因数据源类型、Prompt 长度或工具数量发生变化。

本设计要求业务事实和完整 Schema 不因预算裁剪；查询方言、Helper 签名、产物结构和修复规则按相关能力编译。全部相关必需协议直接注入首次请求，完整组合示例通过同一 ReAct 的 `read_runtime_reference` 可选查阅。不是把所有协议改成必须先检索，也不保证任意规模的 Schema 有固定 Prompt 上限。

当前实施决策与工程门槛见 [方案复核第 8-9 节](runtime-design-causality-review-20260902.md)。历史发现见 [2026-09-02 基线复核](runtime-baseline-audit-20260902.md)。能力清单完整不能代替行为验收。

## 2. 设计原则

- **单一语义所有权**：不新增 Query DSL、Metric Spec、Insight Program 或语义审核 Agent。
- **事实完整，文档分层**：业务事实和完整 Schema 常驻；必需机械协议按能力并集注入，完整参考可选批量查阅。
- **能力并集，不做互斥裁剪**：混合关系、时序、文件分析加载所有相关能力以及跨源能力。
- **契约可验证**：能力由稳定 ID 注册，不再依赖 Markdown 标题位置拼接。
- **同一 ReAct 连续修复**：能力加载、Probe、正式执行和修复都在同一个 Agent 图和消息历史中完成。
- **校验不越权**：Runtime 只做可确定的执行、结构和安全校验；Evidence 语义识别留在成功执行后。

## 3. 分层上下文

### 3.1 洞察语义内核

首次请求固定携带小而稳定的系统 Prompt：数据洞察专家角色、报告质量标准、Preparation 与 Runtime 边界，以及 Probe/澄清/分析/修复生命周期。它只负责洞察语义和决策顺序，不重复机械 API 与数据源方言。

### 3.2 完整分析上下文

首次请求完整携带原始问题、必要会话规则、选定数据源完整 Schema、知识参考定义、带确认状态的关系、用户澄清答案及追问所需记忆；本轮产生的 Probe/执行反馈在同一 ReAct 保留。Preparation 是准备信息，不是指标、查询或报告模板。`unresolved_facts` 为空只表示没有列出的待确认项，不是已证明全部业务语义完整。

### 3.3 能力清单与 Contract Pack

系统按数据源快照确定性生成能力 ID，并在首次模型调用前把全部必需 Contract Pack 编译进 System Prompt。模型无须为了获得必需协议先调用工具；需要完整组合用法时可以查阅参考，不存在“未查阅即拒绝执行”的状态：

| ID | 职责 |
| --- | --- |
| `context.analysis` | 完整 Schema、Preparation、会话记忆和权威事实的解释边界 |
| `execution.core` | Python 闭环、参数、查询约束、Probe、无数据、保存与修复 |
| `query.relational` | 关系查询、SQL 下推、容量和类型规则 |
| `query.time_series` | timescale/vxbase 原生查询、采样和聚合 |
| `query.local_file` | 本地文件和低内存加载 |
| `query.minio_file` | MinIO 对象文件读取 |
| `query.api` | 只读 API 数据访问 |
| `query.cross_source` | 混合数据源查询和跨源组合边界 |
| `result.artifacts` | 图表、表格和报告产物协议 |
| `context.followup` | 追问时的历史结果复用边界 |

Pack 是机械能力知识，不产生指标和叙事计划。混合数据源按能力并集加载，并自动加入 `query.cross_source`。

### 3.4 API 说明与实现同源

各 Pack 注册所使用的 helper 名称，装配时从真实执行命名空间中的函数读取参数签名，保留默认值和关键字参数边界。同一函数在混合能力包中只列一次；返回值与业务使用边界继续人工说明，并通过行为测试核对，不能从类型签名推导业务含义。

协议源码通过 `runtime-helper-reference` 标记放置函数参考。完整关系查询和文件分析示例作为可执行测试夹具，不进入初始请求，但可由 `read_runtime_reference` 读取。查询范围继承等局部示例直接校验并执行，不能只用关键词存在性证明正确。完整参考与常驻协议使用同一文件和真实 helper 签名，没有第二份独立手册。

参考工具只接受已注册 ID，支持批量读取；不查询业务数据、不创建执行记录、不改变输出格式和澄清策略。它不强制增加模型回合；实际查阅的额外回合必须纳入性能验收。无效 ID 不丢掉同一请求中有效的文档，也不触发分析失败或 no_data。

参考加载按当前输出策略提供对应结果说明。文本或 JSON 调用不会通过关系/文件完整示例间接拿到标准图表报告的保存模式；查询能力说明仍完整提供。示例不采用无业务依据的风险阈值，并由独立预期值测试而不是以“代码能运行”证明正确。

## 4. 执行流

1. Preparation 输出选源、完整 Schema 和已确认关系。
2. 后端根据选定数据源快照计算能力并集，编译洞察语义内核、能力清单与全部必需 Contract Pack。
3. Runtime 首次模型调用即同时收到完整分析上下文和本轮可用能力，不经过必需的协议加载工具回合。
   需要更完整用法时在同一循环调用 `read_runtime_reference`，参考的 ToolMessage 与后续 Probe、分析、修复消息连续保留。
4. Runtime 在同一 ReAct 内直接分析、先 Probe，或确需用户澄清。
5. Runtime 调用 `probe_analysis_data` 或 `submit_analysis_program`，二者共用执行底座；执行反馈回到同一 ReAct 并保留原业务口径修复。完成一次 Probe 不关闭后续探测能力；是否再次探测由尚未确认的技术事实决定，不由固定一次次数决定。
6. 成功结果进入后置 Evidence 编译，不反向约束报告表达。

工具观察与可修复错误不使用 `return_direct` 关闭 Agent 图。正式产物保存且执行校验通过后，工具返回内部 `analysis_complete` 状态，由 before-model middleware 在下一次模型请求前结束；不能仅依赖 `Command(goto=END)` 与框架既有工具后续边同时存在的行为。无状态更新的 middleware 会产生空更新事件，流适配层不将其当成消息。该状态不交给模型填写、不代表业务准确性验收通过，也不改变同轮次澄清的挂起/恢复协议。

`probe_analysis_data` / `submit_analysis_program` 的工具选择确定执行用途，模型不必在代码中重复填写 `execution_intent`。执行底座在持久化与校验前把缺失的标识写入完整源码；已有一致标识保持原样，明确冲突返回对应工具的错误反馈。源码补齐保留模块文档、future imports、装饰器和换行语义，后续修复行号、源码签名、执行与本地重跑使用同一份完整版本。原底层 `execute_python` 路径保留原有显式标识要求。

该机制只处理工具已经确定的技术元数据，不补写指标、查询范围、单位、报告表达或业务判断。

## 5. 校验边界

Runtime 可以阻断代码不可执行、只读/安全违规、数据源字段不存在、查询约束确定性不一致、产物结构不可展示、结果未保存或无数据未闭环。

Runtime 不通过后置 Evidence AST 推断并阻断业务指标是否可比。这类发现属于 Evidence 阶段诊断，不成为正式分析循环的额外语义所有者。

## 6. 验收标准

- 关系、时序、文件和混合数据源的 required Contract ID 准确稳定；
- 初始技术协议与完整最终输入分别计量，不能以技术文档缩短宣称整个上下文一定变小；
- 首次模型调用前由后端一次完成必需 Pack 编译，不强制为参考阅读增加模型调用；
- 所有详细参考可在实际 Agent 图内读取，不将只存在于测试文件中的示例算作模型已获得的能力；
- 澄清、Probe、分析和修复保持同一 ReAct；
- 完整 Schema、用户问题和已确认事实不被裁剪；
- 报告表达力不因能力拆包收紧；旧版的查询、参数、Probe、无数据、追问、图表、表格和报告能力必须通过自动化能力对齐测试；
- 每个 Runtime 实际暴露的 API 都必须在至少一个 Pack 中有明确说明；
- 时序方言等精确平台语法通过回归标记固定，不允许在摘要化过程中丢失；
- 既有 Runtime、澄清、图表表格和 Evidence 测试通过。

### 6.1 提交基线能力映射

本次改造是表示和装配方式重构，不是 Runtime 能力重写。提交基线中的能力按下表迁移：

| 基线能力 | 新承载位置 | 不变量 |
| --- | --- | --- |
| 数据洞察角色、统一叙事、动态判断 | `sys_prompt.md` | Runtime 仍是查询、指标、产物和报告的唯一语义所有者 |
| 完整 Schema、字段归属、Preparation 边界 | `context.analysis` | 字段不按预算截断，准备信息不升级成指标/报告模板 |
| Python 闭环、参数、本地重跑、查询约束、Probe、无数据、修复 | `execution.core` | 一份 analysis 代码完成全流程，Probe/修复留在同一 ReAct |
| 关系、时序、本地文件、MinIO、API、跨源查询 | `query.*` | 按已选数据源取能力并集；精确平台方言和容量边界不摘要丢失 |
| 图表、表格、报告表达 | `result.artifacts` | 三类产物共同回答问题，保持业务标签、动态判断和事实建议 |
| 历史摘要、执行记录、旧代码和产物指代 | `context.followup` | 历史帮助承接，不替代当前需要重新执行的数据分析 |
| Evidence | 成功执行后的独立编译阶段 | 不进入正式分析 Prompt，不限制洞察表达 |

自动化门槛同时校验：执行命名空间新增 API 必须有协议说明；关系/时序/混合场景装配全部相关能力；旧版关键方言、参数、Probe、无数据、追问和产物语义均存在；技术协议大小有回归监测，但不以预算裁剪业务 Schema、知识定义或当前执行观察。

## 7. Runtime 查询组合 API

关系型与时序 SQL 的常规路径使用 `query_data_with_sql(...)`，由后端按固定顺序完成查询约束校验、QuerySnapshot 注册和物理加载。本地文件分别使用 `query_local_file(...)` 与 `query_local_file_low_memory(...)`，普通读取和批次迭代都在物理加载前完成同一约束校验；校验语义与物理读取写入同一个 `query_key`，不再制造需要 Evidence 追溯的隐式父子快照。约束失败通过内部控制信号直接转换为结构化 Retry，生成代码不再重复维护校验分支。

`validate_query_constraints(...)` 与 `load_data_with_sql(...)` 继续保留，用于派生范围、多步骤校验等复杂控制流。高层 API 只收敛机械调用顺序，不限制 SQL、跨源分析、指标设计或报告表达。关系型和本地文件的完整组合示例保留在能力包源码中，并经过静态契约和实际 helper 执行测试；在初始装配中省略，按需参考可读取。示例不携带当前业务公式，不作为报告模板；当前 Schema、问题及调用输出协议优先。

Runtime 观测按内容隔离原则记录：语义内核、各 Contract Pack、最终 Prompt 和每轮 ReAct transcript 只记录字符数、估算 token、消息类型与工具调用数；模型响应记录耗时、标准 usage、`finish_reason` 和截断标记，不记录用户问题、Schema、SQL、代码或报告正文。该信息用于区分 Prompt 膨胀、修复 transcript 增长、模型输出截断和真实执行错误。

## 8. 2026-09-02 本地验证状态

本次增量订正了 `get_day_range` 文档：函数保留基线的当日零点与当日最后一微秒行为，没有改成次日排他终点。参数读取继续保留原值与类型，不增加隐式日期转换。父查询范围继承示例读取明细时不再同时声称已聚合。查询组合 API 支持在函数和循环中使用，不以平铺代码作为通用要求。

新增 `tests/test_runtime_capability_behaviors.py`，覆盖签名一致性、真实 helper 与示例执行、范围继承、快照、文件分批读取、参数与时间边界、执行标识持久化及局部修复。联合既有 Runtime/查询/澄清/输出协议测试共 508 项通过，Python 编译及 `git diff --check` 通过。

验证未连接真实数据库或调用模型，不能据此宣称真实报告准确性、表达力、完整 Evidence 或端到端性能已达标。后续依照专项提案进行固定输入 Runtime 对照，再恢复逐会话整体验收。

### 8.1 后续真实对照结论

2026-09-02 后续已在隔离本地数据库中连接 226 FedQuery，以空间 15 会话 48 轮次 70 冻结准备输入进行基线/工作区对照。结果未达业务验收，不能把上面的接口和路由测试解释为性能或正确性已提升。基线 184 秒；工作区修复 Agent 循环后的一轮 336 秒，放开合法源码行修复边界后的一轮 231 秒。样本过少且生成程序不同，不能归因这些耗时差异于单个改动，更不能证明平均性能改善。详见 `runtime-baseline-audit-20260902.md` 第 9 节。

局部修复保留不可变 execution 版本、原行号、范围和不重叠检查，合成后验证完整 Python。合法的参数行、表达式片段和相邻语句修改不再要求恰好等于一个 AST stmt；非法合成仍在创建执行前拒绝。源码原本存在语法错误时，保留编译器错误位置附近的有限修复要求。没有增加程序草稿 Stage 或隐式变量共享。

Probe 查询失败快照现在记录真实 error_type/error_message，`request_retry` 从快照投影 `_query_execution_outcomes`，避免生成代码只复制 row_count 而丢失错误。该字段只来自实际快照；失败不被转换为无数据，未执行路径不补造执行结论。此增量覆盖现有 SQL loader（关系与时序共用）的异常路径，不声称其他所有 loader 的异常细节已补齐。

### 8.2 实际装配和校验证明边界

实际送入 Runtime 的数据源项决定查询能力包，不再独立依赖调用方是否传入 snapshot_override；会话内部加载的 Schema 同样携带对应能力元数据。该元数据只用于本地装配，不新增数据源查询或模型调用。

静态预检只能在可证明的变量绑定与调用点值上阻断。函数作用域、重赋值、动态补列、闭包消费等不支持的推断保留 unknown，由实际执行反馈处理。参数的数据依赖不能自动升级成父实体范围继承；显式范围声明和物理查询校验继续生效。当前修复说明完整传递，Python 与报告位置分开，局部源码范围必须匹配失败版本。

这些修正及固定程序对照见 `runtime-baseline-audit-20260902.md` 第 10 节。首轮语义完整性、业务算法与最终表达仍需独立真实验收，不因接口测试通过宣布设计目标达成。

### 8.3 2026-09-03 工程门槛

已落地只读参考查阅、刷新路由单一来源、知识定义完整交付、准备信息的确认状态边界，以及按输出策略提供参考示例。20 个相关测试文件共 406 项通过，覆盖真实 Agent 图、取消、无数据、澄清和外部输出。实现清单与剩余业务验证见方案复核第 9 节；本轮未发起新的真实分析，不宣称业务准确性或端到端性能已优于基线。
