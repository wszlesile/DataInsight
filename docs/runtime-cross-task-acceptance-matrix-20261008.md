### Design diagnosis from the two task families

The earliest wrong point in this new sample is **after** the computations: the model received the correct product totals, per-product distribution, costs, the original question, and an empty decision-condition list. It still authored a cause (“pricing strategy”), a cross-dimension explanation (“rather than production cost”), and a source-completeness assertion. The device sample showed the same transition from correct distributions into unsupported operational meaning. This points to an expression ownership gap, not a query/cost calculation defect.

The current data path gives the expression model factual calculation results and a prose `descriptive_only` boundary. It does not give each narrative conclusion an authoritative typed identity or a computation/criterion binding. Existing query receipts and semantic calculation facts establish where values came from; they do not establish that every sentence in the report is an allowed inference from those values. Adding a post-hoc sentence checker would move that gap into an unsupported semantic validator, which is explicitly outside the accepted approach.

A design candidate therefore has to make the *generation path* own the boundary. It should distinguish at least: (1) observed facts, (2) deterministic mathematical comparisons derived from facts, (3) rule-based business decisions with an explicit criterion and source, and (4) causal claims requiring a causal method and supporting inputs. A missing criterion or source must remain absent in the expression state; the system may ask a same-turn clarification only when the answer materially changes the requested conclusion. Evidence should link to these producer-owned objects, not retroactively certify free text.

### Code-level contract audit

- `src/analysis_runtime/semantic_execution.py` exposes executed `FactRef` values and a `DecisionRef`; its persistent decision object is currently `define_extrema` / `evaluate_extrema` (max/min). Separately, `src/analysis_runtime/calculations.py` and `expressions.py` provide value-level numeric comparisons and ratio helpers, with caller-authored comparison templates. These helpers can calculate relation/difference/relative change, but they do not create a source-bound persistent general decision/finding identity. `render_value` creates a provenance-tagged numeric fragment; `render_extrema` creates a mathematical extremum fragment. None represents causal attribution, population completeness, or a general criterion-backed business decision.
- The same module accepts arbitrary `PythonCalculation` callbacks. `src/analysis_runtime/semantic_evidence.py` consequently marks these as `execution_only`, with reason `custom_execution_does_not_prove_input_field_usage_or_formula_correctness`; business semantics are explicitly `not_evaluated`.
- `src/analysis_runtime/provenance.py::compose_report` preserves receipts for registered fragments but also concatenates ordinary string parts. This is useful for authoring flexibility, but means the producer does not own every semantic assertion in the resulting document.
- `src/analysis_runtime/semantic_evidence.py::attach_semantic_presentation_bindings` can bind numeric report spans and structured artifacts to facts. It does not create an authoritative identity for nonnumeric sentences such as “pricing strategy caused the difference” or “the source population is complete.”
- The expression contract already says not to add unsupported causal explanation under `descriptive_only`; the cross-task first response violates that instruction. The missing piece is therefore not another prompt sentence or a missing field in the output contract.

### Candidate design to prototype

Keep the current one-call expression stage, but change its product from unrestricted Markdown to a structured report composition over producer-owned findings. Findings should carry stable identities, population/grain, values, units, method, and source fact IDs. The executable layer should natively produce descriptive findings and mathematical comparisons; a business finding should require the criterion and source reference; a causal finding should require a supported causal method; a completeness finding should require authoritative source-coverage metadata. The expression model may choose ordering, headings, and restrained connective text, while the host renders the claim-bearing sentences from the finding records. This is a generation-time boundary, not a semantic review of generated prose.

The key risk is loss of naturalness. Do not implement the proposal until a small prototype shows that its claim-bearing output can still answer both the product-margin and device tasks with similar analytical breadth and readable narrative, while making it impossible for free prose to add a causal or completeness assertion. If arbitrary claim-bearing prose remains, the boundary is not enforced. If only rigid boilerplate works, that is an unacceptable regression to measure and reject rather than hide. The first prototype should use the already calculated facts and current candidate findings, add no model invocation, and compare report expressiveness and token/time cost. Only after that should both isolated cases be rerun.

An offline first prototype now exists beside the expression trace: `typed-findings.json`, `typed-renderer-prototype.md`, and `render_typed_findings_prototype.py`. It renders seven typed findings (aggregates, comparisons, ranking, separate metric rankings, and a source-coverage limit), plus product profit and cost-composition tables. It is 1,204 characters, includes the requested cost/profit comparisons, and uses zero model calls. It avoids unsupported pricing/cause claims and does not declare the selected files complete.

The same renderer direction has now been exercised on the device task. `render_device_findings_prototype.py` reads the exact local workbook named by the saved r19 Schema and independently recomputes all seven fact groups; all seven match the saved r19 candidate (`device-source-fact-check.json`). Its 1,348-character report covers device count, all type/status/location/manufacturer distributions, installation-year counts, and rated-power statistics. It does not infer operational health, supplier risk, expansion/renewal, population completeness, or actual facility load. The original model report was 2,064 characters; this renderer is shorter while retaining every computed dimension and replacing unsupported interpretation with explicit scope. This is an offline controlled comparison, not a current Worker or full-pipeline rerun.

Together, the two prototypes suggest a compact deterministic claim-bearing layer can preserve task-family factual coverage at zero expression-model calls, but the text is less free-form. The next design spike is to map these finding kinds to Runtime-produced results and existing artifact lineage, then measure how the production API can keep natural connective narrative without permitting new claim-bearing prose. No production code should change until the `PythonCalculation` evidence limitation and arbitrary-string report path are addressed at that same boundary.

### Closed report AST check

The first renderer prototype stored `rendered_text` on each finding, which left the very free-claim field the design is meant to remove. That version is retained as an initial experiment, not treated as proof. A second offline prototype now uses a Pydantic discriminated `Finding` union (`aggregate`, `distribution`, `comparison`, `ranking`, `table`, `coverage`) and produces the same two reports without a `rendered_text` field. `extra='forbid'` rejects unmodeled top-level claim fields. It renders the product case in 1,109 characters and the device case in 748 characters; the output is notably more compact/less narrative than the model reports (1,583 and 2,064 characters), while keeping their calculated dimensions and rows. It uses no model call.

This still is **not** a production-safe closed contract: titles, metric labels, column labels, and nested dict values remain ordinary strings/dicts, and the offline constructors are trusted Python rather than runtime-validated source bindings. A generated program could mislabel a field or put an unsupported assertion into one of those strings. The next refinement must replace claim-bearing labels with registry/schema references and make each typed finding resolve only to executed result IDs and supported operations. The experiment proves the possible size/coverage shape, not that the current runtime enforces it.

There is a hard design constraint to resolve honestly: if the final report remains unrestricted free-form model prose, no prompt, fact citation, or self-declared confidence can guarantee that it will not introduce an unsupported claim. A deterministic renderer over typed claims can guarantee the boundary, but may reduce narrative freedom. A hybrid must prove how narrative wording can stay rich while semantic authority remains with typed results, without quietly relying on another LLM review or an output-level semantic filter. If that cannot be demonstrated, record the accuracy/expressiveness tradeoff as unresolved instead of claiming that the current design can guarantee both.
