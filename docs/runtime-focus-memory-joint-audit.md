## 本轮落地及证据边界

已修范围是实现态 Schema 补读、全局覆盖状态及待确认技术项的可见性，
不修改查询、Probe/no-data 或正式代码规范。
补读内容由真实 reader 产生，通过工具结果交给下一次请求；不把所有过去读取
字段重新并入 system prompt。测试覆盖直接请求投影及 create_agent 实际工具
循环。它证明补读路径可达，**不证明全部上下文去重、生命周期或真实分析质量
已经达标**。

本轮验证：working_context、workspace、datasource_context_runtime、prompt_loader、
prompt_capability_parity 合计 168 项通过。实际 create_agent 测试使用脚本模型，
真实执行 Schema reader，再检查下一次模型请求；不把脚本模型测试等同真实
LLM 准确性评估。本轮没有启动服务、远端更新或发起真实分析。

后续增量：实现态恢复 select_runtime_work，工作事件回放在 Probe 内保留父工作
与焦点。来自 repair 的 Probe 成功返回 repair；来自材料计划的 Probe 返回
该计划的正式分析焦点，而不是保留探测标题。未修改 Probe 的执行职责、事实
格式或 no-data 判断。现在不再要求先提交失败程序才能进入探测。

实际 create_agent 脚本测试延伸为 plan -> 实现 -> 真正 Schema reader ->
选择新探测依赖 -> 脚本 Probe 观察 -> 恢复实现 -> 提交。验证每次实际绑定
工具、加载协议、返回焦点、查询观察和原始消息存储。另测 Probe 自身失败
后修复成功仍能回到原程序修复，并保留当前完整代码。连同 clarification、
execution_history 等相关测试共 228 项通过。此结果仍不是整体验收。

本轮没有消除所有缺陷：材料范围的父子工作恢复、业务判断细节的补载、旧
诊断/判断的有效性、外层与澄清恢复的数据等价性仍按表跟进。重复选择同一
工作是否形成无进展调用也必须实测，不能再通过封死合法探测来掩盖。

下一步按上表 P0/P1 顺序补齐联合行为测试，再选择一个简单及一个需要 Probe

端到端耗时，并人工复核结论、数值、图表表格及引用。

## 语义判断与修复粒度不变量

- 不得依据“本周期”等词面命中结果建立澄清硬门控。只有互斥解释会实质改变计算正确性，且上下文、
  Schema、业务规则和 Probe 均不能消歧时，才由 Runtime 在同轮次请求用户澄清。可合理采用并披露的
  口径继续分析。
- 错误类型不是业务规则。后端只对能够定位到完整 Python 语句范围的确定性技术错误提供
  `repair_target`；模型必须以该次真实执行源码为唯一基线，仅修改允许范围。
- 查询范围、字段归属、JOIN、聚合、指标公式和报告语义无法由局部源码范围证明时，仍走完整程序修复。
  不得为了减少重试而把业务表达收紧成局部补丁。
- Probe 失败或被拒绝属于执行反馈，不得登记为 `probe_observation`，更不得进入 Probe 事实账本。
  只有带结构化事实账本或真实查询快照的成功观察才会改变 Probe 生命周期。
