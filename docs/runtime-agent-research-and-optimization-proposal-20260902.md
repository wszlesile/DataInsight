## 1. 结论

建议继续保留 **Preparation -> 一个统一 Runtime ReAct -> 后置 Evidence**。下一步不是换框架，也不是重新把查询、指标、图表和报告交给不同语义规划阶段，而是完善统一 Runtime 的工作环境：

1. 核心业务事实持续完整，技术参考按用途分层交付。
2. 把系统已知、可确定执行的机械工作从模型职责中移出，减少同一事实的重复填写。
3. 以实际查询观察、程序版本和明确错误为反馈依据，在同一 ReAct 中继续分析与修复。
4. 保留完整 Python 作为最终交付；复杂任务是否需要可选的程序草稿编辑能力，单独实验，不一次性引入。
5. 将业务正确性、报告表达、Evidence 和性能分别验收，不能以技术执行成功替代整体通过。

这是一条有依据、与现有代码相容的优化方向，**不是已经证明的全局最优方案，也不能保证任意小模型在任意分析问题上一次成功**。应先消除工程层人为增加的负担，再测模型真正的能力边界。

## 2. 调研范围与适用边界

调研官方文档和公开源码，不把厂商的产品宣传准确率作为本项目的效果承诺。公开源码使用所读取的 main 快照，产品文档使用访问日版本；其中 Snowflake 架构文章发表于 2024 年，作为公开设计说明，不假设其仍是最新内部实现。

### 2.1 通用 Agent：上下文随执行管理，而不只是改 System Prompt

Anthropic 的上下文工程文章区分了固定提示词与每次推理的上下文管理，介绍了预加载与按需查阅相结合的方法，同时明确指出检索有延迟成本、过度压缩会丢失重要信息。对我们的启发是：协议文件拆开并不等于完成上下文工程，应检查每次真正送入模型的内容及其生命周期。[官方资料](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

OpenAI 的函数调用指南建议由代码提供系统已经知道的参数、合并总是连续执行的操作，并清楚描述输入与结果。对本项目而言，首先应减少重复约束声明和错误处理样板，而不是让模型用更多工具逐个创建指标。[官方资料](https://developers.openai.com/api/docs/guides/function-calling)

LangChain 的公开实现通过 middleware 区分每次模型调用的临时上下文与持久状态。这说明我们现有 `create_agent` 已有可利用的扩展点，不必为了上下文管理重新搭一个 Workflow。是否使用具体 middleware 还需按本地依赖版本测试。[官方资料](https://docs.langchain.com/oss/python/langchain/context-engineering)

### 2.2 数据分析产品：业务语义不是靠通用模型猜出来的

Snowflake 公开设计采用语义模型、相关示例查询和纠错等机制；其 Verified Query Repository 存放经核实的问题与 SQL，服务相似问题。值得借鉴的是业务知识来源及验证机制，不是把我们每轮报告先限定为固定指标表。[架构说明](https://www.snowflake.com/en/blog/engineering/snowflake-cortex-analyst-behind-the-scenes/)；[VQR 文档](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)

Databricks Genie 强调字段元数据、业务表达式和经核实的查询示例，避免全部塞入自由文本指令；它也通过 benchmark 问题测试效果。但其聚焦主题、收窄表范围等建议不适合直接照搬为我们的选源限制，SQL 答案质量也不能等同于完整洞察报告质量。[上下文建设建议](https://docs.databricks.com/aws/en/genie-agents/best-practices)；[测试与监控](https://docs.databricks.com/aws/en/genie-agents/monitor)

对我们的推论：Schema 足够完整时，应改善模型读取和执行；Schema 缺少业务定义时，需要用户知识、经确认的规则或澄清。Prompt 再好，也不能从数据分布证明“月份必须按开始时间归属”这样的业务约定。无需为每个临时分析强制建立企业级指标库。

### 2.3 可执行数据分析 Agent：统一分析者可以拥有按需能力

Microsoft Data Formulator 的公开 AnalystAgent 源码展示了统一分析循环、基础能力、按需加载 skills，以及观察结果返回同一循环的组织方式。它不是把所有报告语义预编译成指标 DSL。[Agent 源码](https://github.com/microsoft/data-formulator/blob/main/py-src/data_formulator/analyst/agent.py)；[核心能力说明](https://github.com/microsoft/data-formulator/blob/main/py-src/data_formulator/analyst/skills/core/SKILL.md)

但是它的交互式产物动作和探索过程，不能直接替代我们必须落盘的一份完整可重跑 Python。我们借鉴能力交付与观察反馈，不照搬其逐个发布产物、委派方式或报告生成协议，也未在本地运行该项目来验证性能。

### 2.4 不能从调研推出的结论

- 不能声称主流 Agent 都采用单 Agent。公开系统既有统一循环，也有多 Agent 和固定流程。
- 不能因为其他系统有 skills，就声称延迟加载一定比当前快；它可能多一次模型调用。
- 不能把商业 SQL Agent 的准确率迁移成我们的多源 Python、叙事和 Evidence 准确率。
- 不能仅凭 Prompt 长度断言其是报告退化的唯一原因。需要把模型理解错误、接口错位、准备信息缺失和真实数据变化分别排除。

## 3. 当前代码事实与差距

### 3.1 已有基础应保留

| 能力 | 当前实现 | 判断 |
| --- | --- | --- |
| 统一分析循环 | `src/agent/__init__.py:create_data_insight_agent` 使用 `create_agent`，提供 Probe、正式提交及可选澄清 | 架构基础可继续使用 |
| 连续修复 | `invoker.py:_merge_agent_round_messages`、`_new_agent_round_messages` 保留同一轮的 AI/tool 消息 | 不重新创建缺少原分析历史的 Repair Agent |
| 程序级执行 | `tools.py:submit_analysis_program` 支持完整代码和 `base_execution_id + patches` | 有条件减少全文重写，最终仍执行完整程序 |
| 查询组合操作 | `query_data_with_sql` 固定完成校验再执行；文件也有组合 helper | 符合减少模型机械职责的方向 |
| 多源能力并集 | `runtime_contract_registry.py` 根据全部选源类型加载 SQL、时序、文件等及 cross_source | 混合查询不能只保留一种方言 |
| 独立结果策略 | standard/text/json、是否允许澄清由当前调用策略决定 | 不能让标准报告要求污染外部 JSON 调用 |
| 后置 Evidence | 正式代码继续不承担 Evidence 编写 | 本方案不把指标建模职责塞回正式代码 |

这些不是本提案新发明的能力。后续要解决的是它们的使用成本、职责重复和端到端一致性。

### 3.2 仍需优化的具体位置

**一、当前是按类型选择后一次注入，不是逐次上下文管理。**

`required_runtime_contract_ids()` 确定包；`load_runtime_contract_prompt()` 加载全文；`build_prompt_messages()` 将数据源、协议、语义内核等合并为系统消息。相关能力一多，初始技术文档仍随之增长。目前没有查阅 Runtime 参考文档的工具，也没有按模型动作管理技术文档的 middleware。

现有历史测量：纯协议文本约为关系型 22,052 字符、关系+时序+文件 29,033 字符；r11 首次实际模型输入约 24,235 token，正式提交前约 27,847 token。这些是此前测量，不是本轮新测量。

**二、能力包仍以手写说明为主，没有形成可验证的 API 文档单一来源。**

`RuntimeContractPack` 目前主要登记 ID、文件名与描述。真实 helper 签名、Tool 参数说明、规范示例、校验器和错误修复指南分别维护。代码名称相同、测试含有某关键词，并不能证明模型看到的调用方法与实际行为一致。

新发现的具体风险：`execution_core.md` 父子查询示例实际选择原始事件行，却声明 `aggregation.grain='batch'` 和 `metric='event_count'`，与同文件“按物理返回粒度声明”的规则不一致。另有“平铺查询，不把 loader 放在多层函数/循环动态定义”等限制，仍反映用代码写法迁就观测或解析能力的问题。这里只记录，不能用这种限制作为未来架构前提。

**三、同一项工作仍要求模型提供多份相互关联的表示。**

`query_data_with_sql` 接受 SQL、query_constraints、filter_expressions、aggregation_hints、sql_context 和范围继承信息。其中有些是必要业务声明，有些是技术重复。不能整体删掉，但应逐项确定权威来源。`probe_analysis_data` 与 `submit_analysis_program` 已区分用途，模型还必须在代码里重复声明 execution_intent。

这里“减少重复”的前提是系统确实已经知道事实；不能通过猜测 SQL 语义或隐式改日期，替代模型真正需要决定的业务范围。

**四、一次正式提交依然承担整份程序构造。**

现有 patch 主要针对失败执行中的允许源码范围；没有供复杂任务逐步编辑、尚未执行的程序草稿能力。普通任务这样最省调用，复杂任务却可能同时承担业务推理、方言、参数、图表、报告和结构规范。是否要改变这一点，应单独做实验，不能直接再拆一个 Brief 阶段。

**五、反馈现在更一致，但还不是业务正确性的证明。**

上一轮已修复任务隔离、Probe 观察分类、无数据事实继承和部分未知语法误拒绝。r11 的业务判断、准备血缘缺失及 Evidence partial 仍没有在线回归验收，不能因此宣布已解决。Schema 缺少业务依据与代码不符合技术协议，需要不同处理方式。

## 4. 建议的目标设计

### 4.1 流程不增加新的语义 Stage

```text
Preparation：业务意图、选源、完整 Schema、关系和业务支撑信息
    |
    v
统一 Runtime ReAct
    模型决定当前需要什么
      -> 读取技术参考（可选）
      -> Probe 核实技术事实（可选，可再次使用）
      -> 同轮次澄清真实业务歧义（按调用模式）
      -> 生成完整 Python / 修复已有程序
      -> 执行并读取结构化观察
    成功输出完整可重跑程序与分析产物
    |
    v
后置 Evidence -> 保存/展示
```

动作可以直接跳到正式提交，不固定要求走齐上面所有步骤。查询、计算、判断、图表、表格、报告仍由同一个 Runtime 整体决定。后置 Evidence 的语法覆盖问题另行推进，不借本次上下文改造侵入正式分析。

### 4.2 信息按来源和生命周期交付

| 信息 | 默认如何交付 | 不允许的处理 |
| --- | --- | --- |
| 问题、会话提示、输出要求 | 持续保留，明确当前轮次和调用模式 | 被错误反馈改成更窄的任务 |
| 选中来源的完整 Schema、相关规则、关系 | 持续保留，去重但不丢字段、定义和来源 | 用预算静默删字段、少选源 |
| 用户澄清答案 | 原文保留，并记录问题与适用范围 | 压成不可追溯的模型猜测 |
| Probe 观察 | 查询标识、实际口径、状态、类型/枚举/覆盖及必要小样本 | 把样本当正式指标、把一次观察当所有路径已确定 |
| 核心执行协议 | 初始保留，覆盖只读、参数、终态、空数据与修复 | 延后到写错代码才告诉模型 |
| 常用 API/相关方言入口 | 初始提供足够可调用的签名和短例 | 只有名字没有参数、返回值语义 |
| 少见参数、长例、高级图表配置 | 全量可查阅，不默认重复注入 | 为省 token 永久删除能力 |
| 当前程序和错误 | 同一 ReAct 中保留版本关系、确切反馈 | 换 Repair Agent、只给错误摘要而丢原分析 |

“完整语义”不等于“每次都复制全部技术参考”。但完整 Schema 与核心业务信息构成不可消除的上下文下限。在不改变该要求的前提下，不能保证输入对任意来源规模保持固定大小。

### 4.3 能力包从文档目录升级为可测试的能力定义

优先扩展现有 registry，不增加一套与之并行的框架。每个能力包明确：

- 适用的数据源/调用模式、依赖包和版本。
- 已实现的 helper 及真实调用签名。
- 默认展示的最小可用说明。
- 可查阅的完整参数、返回值、错误语义与复杂用法。
- 可执行的技术示例和正反测试。

签名从实际 callable 或 schema 校验，业务说明仍由人工维护；不能认为自动提取 Python 类型即可生成完整好文档。示例必须通过真实 helper 的测试路径，包含合法与错误用法，不能只有字符串存在性检查。

新增一个只读参考查阅工具即可，支持一次读取多个主题；具体命名在实现时确定，不把每个 helper 都暴露成单独的 Agent Tool。初始自动装载当前所有源类型的常用查询说明及所选输出格式说明。混合 SQL/时序/文件不会因只装某一种而丢能力。

模型若无需额外参考，不增加 LLM 调用；确需查阅时通常会多一次模型往返，所以必须测总成本。已加载的参考在当前循环中去重并保留，不宣称加载一次后自动从后续请求中消失。先不引入有损历史压缩；未来要移除旧内容，必须另做恢复与召回率验证。

能力包版本固定在本次任务中，澄清挂起/恢复也延续同一版本和已加载清单；避免应用更新后原程序与新文档突然错位。

### 4.4 工具/API 优化：让模型少写机械内容，不是少做分析

优先梳理现有 helper，不重新建立 metric API：

| 模型继续决定 | 系统可以负责 |
| --- | --- |
| 对象、总体、时间归属、公式、比较方法 | task/turn、认证、执行环境等已知参数 |
| SQL/原生时序表达式、文件变换 | 校验与快照注册的固定顺序 |
| 选择采样/聚合及窗口 | 已选择方案对应的连接、包装与执行 |
| 空路径是否影响业务问题 | 真实查询成功/空集/失败及截断信息 |
| 报告判断、条件句、图表和表格表达 | 结构序列化、产物索引及保存的机械步骤 |

具体推进点：

1. 执行用途以工具动作作为系统已知事实；重复的代码标识如何规范化及导出，先验证现有静态检查和本地重跑，不强制让模型维护两个来源。
2. 保留 query_constraints 表达业务意图；物理语句和 params 只传一份，观测、校验和快照引用同一份。对 sql_context 等重复技术描述，仅在底层 API 确定能够提供时自动填充。
3. 原生 SQL、vxbase/timescale 及文件处理继续开放。不能发明一个必须覆盖所有方言的万能 DSL，也不能为解析方便禁止正常函数、循环或合法查询组合。
4. 来源范围区分允许候选、计划访问、实际成功/空集/失败查询，不用其中一种自动替代其他种；只有观测能可靠解析的部分由系统记录，未识别不冒充未查询。
5. 参数 helper 保留值与类型。时间语义由明确字段/参数定义决定，不再在基础读取层隐式改时区或边界。

这部分必须做 API 级局部变更和对照测试，不一次改全部查询协议。复杂逃生路径继续保留，系统不支持推导时保留显式元数据，而不是拒绝合法分析。

### 4.5 反馈是事实，不是一份新的分析计划

复用现有 task、execution、QuerySnapshot，不另造一个业务定义大对象。统一反馈字段的来源和含义：

- 本次执行的 task、execution、代码版本。
- observation / error / success，区分技术未知与确定失败。
- 哪条真实查询、哪个参数或源码位置；已执行和未执行路径不能混淆。
- 可证明的错误与尚未证明的问题分开，后者不自动触发整段重写。
- 实际修复所需的签名、参数、相关短例，只给本次错误相关内容。
- 输出格式和澄清开关来自调用策略，不在反馈中另写一套相反要求。

未知语法不等于业务错误；但能执行也不等于业务正确。已经知道明确公式时可检查实现是否一致；没有权威公式时应由 Runtime 判断是否需要澄清，不生成一套公式后再自证正确。

### 4.6 复杂程序的可选编辑能力：暂列第二阶段实验

当前主要负担之一是整份程序一次生成。可实验允许同一 Agent 写入、读取和修改一个 Python 程序草稿，再提交完整程序。复用 execution 源码及 patch 机制，补足未执行版本、版本校验和读取能力。

关键边界：

- 草稿是 Python 源码，不是 Brief、报告模板、Metric Spec 或业务 Blueprint。
- 不要求先后编写“指标段、图表段、报告段”，模型可整体修改。
- 不共享隐式 DataFrame/变量，不把多个 notebook cell 当最终任务。
- 草稿编辑不查询数据库、不保存业务结果，也不被计为失败执行。
- 每次最终执行使用完整版本；本地重跑无需此前聊天和编辑记录。
- 简单问题仍直接提交完整代码；不增加所有任务的固定调用次数。
- 编辑操作绑定当前任务与确定版本，取消后不得继续发布结果。

收益假设：复杂问题的局部修复更小、减少整份报告被重写；风险是调用增多、模型重复编辑、状态管理变复杂。当前未证明该能力一定需要，因此不与第一阶段一起实施，也不把它作为本轮验收前置。

## 5. 一个具体执行例子

问题同时涉及关系型的设备事件和时序传感器：

1. Runtime 一开始看到完整业务问题、两类 Schema、关系，以及两类常用查询接口，不先生成固定指标清单。
2. 模型决定是关联分析还是并列对照；如果采样语法细节不确定，查阅对应技术参考。文档查阅不改变选源和分析意图。
3. 存储格式/枚举未知时，生成有界 Probe，观察返回具体 query_key、时间字段、真实值和查询状态。观察不能被解释为完整正式分析。
4. 只有业务定义确实影响答案且现有信息不能消除时才澄清。例如业务周期到底归属哪个事件，不能靠样本猜企业约定。外部调用不能挂起时，按该模式表达不确定性，不偷偷猜公式。
5. 模型生成一份完整 Python，用正式查询重新读取本次执行的数据，计算、对比、作图和写动态叙事。
6. 若图表参数错，反馈该调用和正确接口，修复同一程序；不能要求删除时序部分换取通过。
7. 成功后才进入后置 Evidence。其覆盖率和公式正确性单独验收。

这说明我们需要细化的是“如何获得事实、使用技术能力、修复程序”，而不是将一份洞察的业务构思拆散。

## 6. 与历史方案的实质差别

| 历史尝试 | 本提案不重复的点 |
| --- | --- |
| Frame/独立语义规划硬契约 | 不新增前置指标和章节规划；Runtime 仍有最终判断权 |
| DSL -> metric -> insight program -> code | 不以固定指标 spec 接管报告；Python 保留原生表达 |
| Brief/伪代码先规划报告 | 不强制第二次模型照抄某份报告计划 |
| Workspace 业务大对象 | 当前状态以真实代码、查询观察和用户补充为基础，不要求填满业务定义对象 |
| 单纯拆分 Prompt 文件 | 从真实 API、可执行示例到调用上下文形成一致来源，而不只是移动文本 |
| 按预算压缩核心资料 | 完整 Schema/业务规则不裁剪；减少重复和不常用技术手册的常驻 |
| 修复 Agent 独立处理 | 仍在原 ReAct 和代码版本上修复 |

## 7. 分步落地与退出条件

### 第一步：冻结行为对照，补足能力可验证性

涉及现有 registry、prompt loader、相关 tests 及基线审计记录。建立“能力 -> 实现 -> 模型实际可见说明 -> 可执行正反例”矩阵，修正示例与实现错位。保留当前已做的任务历史/反馈修复。

完成条件：SQL、时序、文件、混合查询、空集/部分数据、参数重跑、同轮次澄清、standard/text/json 的原有能力均有行为验证。测试不能只证明某个词还在 Prompt。

### 第二步：逐项消除机械重复

从执行用途、固定校验注册顺序、已知执行参数和重复 API 描述入手；再处理可确定的查询技术元数据。主要改动边界是 `tools.py` 相关 helper 和协议测试，不动 Preparation 职责、Evidence 或查询业务语义。

完成条件：同一合法分析程序的结果、范围、参数和 QuerySnapshot 不变；非法调用仍可准确定位；没有因技术封装增加额外模型调用；本地重跑仍独立可执行。

### 第三步：实验常驻核心与按需参考

扩展 registry、`build_prompt_messages` 与 Agent 只读文档工具；必要时用 middleware 给每次推理装配去重上下文。保留完整业务资料及同一 ReAct。先不更换模型供应商、传输方式或总轮数。

完成条件：必需协议可用率没有下降、混合源能力不丢、澄清恢复不丢文档状态；比较首包及累计 token、调用次数、全链路耗时和首次成功率。若查阅成本大于收益，应调整预加载范围，而不是减小分析范围。

### 第四步：只有必要才实验程序草稿

前三步完成对照后，如果错误仍集中于长程序整体生成和技术修复破坏业务内容，再实现 4.6 的可选编辑能力。它是中等以上工作量的独立实验，不纳入前面三步的最小版本。

### 第五步：先 Runtime 对照，再整体验收

- A：已提交基线；B：当前修复后的工作区；C：每一步候选改动。避免把所有未提交改动同时当成一个因素。
- 固定问题、会话记忆、准备结果、Schema、模型设置及数据时间范围，先做 Runtime-only 对照；再恢复真实 Preparation 全流程。
- 沿用 226 空间 15 的顺序回归，覆盖 43/44/45/46/47/48；环境、轮次和认证重新核实，不猜当前实际数据。
- 补充时序/文件/混合、无数据/部分数据、追问、真实澄清、外部 JSON、本地参数重跑等能力用例。多环境能力不能用关系型样例代替。
- 每个候选机制重复测量并保留失败。建议重要代表用例每版本至少 3 次作为初步筛查；这不足以统计证明高可靠性，验收批次还要扩大样本及独立问题。
- 不并发轰跑。逐会话保留轨迹，再统一归因，问题不能因换会话而消失。

验收记录：关键指标独立核算；公式、统计总体、时间、单位正确；业务判断与数值一致；图表/表格可用；报告有解释与事实支持的建议而非章节堆砌；Evidence 的定义、引用与值准确完整；小模型和主模型分别记录首过率、一次修复成功率、调用数、输入/输出 token、端到端耗时。

表达力使用同问题基线盲对比，不能只数章节、图表或字数。构造对照数据让趋势方向、排名或有无数据发生变化，检查同一代码的判断是否随真实结果变化。没有业务权威定义的指标不能把某个模型答案当金标准。

若技术错减少但报告退化、同问题跨次不稳定、或总耗时持续上升，应停止叠加功能并复核该步假设，不以收窄能力或放松准确性验收补救。

## 8. 调研完成时的边界与建议决策

本轮完成了公开设计调研和当前实现对照，只新增本文。未进行新的在线验收，未修改现有架构文档为“已实现”，未调整 API、Prompt 或代码执行行为。

建议先批准第一、二步的细化设计和小范围实现，按独立增量验证；第三步的默认预加载边界需要通过真实任务对照选择；第四步暂不实施。不要把所有可借鉴做法一次塞进 Runtime。

最重要的变化不是“再细分几步”，而是：**统一模型负责业务判断，系统减少重复技术劳动，事实与不确定性有清晰来源，反馈帮助修好同一份分析程序。**

## 9. 获准后的第一、二步实施记录

本节记录用户批准继续推进后的首个代码增量，不改变第 8 节所记录的调研时点，也不把第三、四步标记为已实现。

### 9.1 已实施的修改

1. **API 签名与真实实现同源**：`runtime_contract_registry.py` 为能力包注册 helper，读取实际执行命名空间的函数签名，保留关键字参数限制与默认值；混合能力包去重。返回语义仍明确人工编写，不自动猜测。
2. **订正确定的说明错位**：`get_day_range` 实际是包含式日终，订正文档而不改 helper 或暗改时间；父子查询示例不再将读取明细声称为聚合结果。常规函数、循环组织查询不再被提示词要求改成平铺代码。
3. **工具确定执行用途**：Probe / 正式提交工具向底座传入用途，模型无需重复声明；底座在保存前补齐完整源码的执行标识。相符声明不改写，冲突明确反馈；保留同一源码上的补丁修复与独立本地重跑。
4. **增加行为验证而非只测文本**：模型可见 API 签名、协议中的局部示例、执行命名空间与真正的校验/快照/产物 helper 一起验证。物理数据库访问在本地测试中替换为固定数据；另有真实临时 CSV 分批读取用例。

未改变 Preparation 职责、Schema 内容、模型供应商、LLM 传输、总轮数、业务计算方式、输出格式、同轮次澄清或后置 Evidence；未新增模型调用。既有查询组合 API 的校验与注册顺序没有重写。本轮也没有将无法确定的查询元数据自动推断成事实。

### 9.3 结果、性能与后续门槛

- 18 个相关测试文件共 **508 项通过**，耗时 7.76 秒；新增行为测试文件含 54 项参数化用例。Python 编译及差异空白检查通过。
- 本轮没有新增在线分析、数据库回写、服务启动、部署或 Git 提交。
- API 反射读取有进程内缓存，不增加模型调用。SQL/时序协议字符数略减，三类混合源协议字符数略增；不能把消除重复参数误称为 token 或全流程耗时已经下降。
- 目前仍一次注入全部相关协议；只读技术参考加载、能力包版本锁定和 Python 草稿编辑均未在本轮实现。
- 下一步先固定问题、Schema、准备结果与模型配置做 Runtime 对照，检验技术误用和重复填写错误是否减少，同时检查报告内容与调用成本。保留失败记录；此前 r11 的业务准确性与 Evidence 缺口不能用这组本地测试注销。
- 若本增量行为对照无回退，再单独开展第三步的预加载/按需参考实验；不要在尚未对照时叠加新的状态管理机制。

### 9.4 对照后的决策更新

固定 226/15/48/70 的准备输入后，基线用时 184 秒；当前两次完成结果的对照分别 336 秒、231 秒，均未满足业务正确性与覆盖验收。单次输入减少并没有证明整体稳定性与准确性提升。真实记录、独立 SQL 核算、基线已有问题与未提交回退的区分见 `runtime-baseline-audit-20260902.md` 第 9 节。

因此第三、四步继续暂缓。已修复确定的工具提前收口、查询错误事实丢失和合法行级修复被拒问题；未扩大 Preparation、指标建模或 Evidence 的职责。用户指出回退后，完成运行中的测试即停止新回归，不以继续多跑来替代归因。下一次推进须先证明相关机制的局部正向影响，不能以本轮执行成功作为整个候选版本可验收的声明。

后续复核再次发现新增预检将语法推断误认为确定事实、能力包与实际 Schema 分别装配，以及修复反馈的位置/截断错位，已按专项审计第 10 节订正。不能把“更多预检”作为小模型正确性的保证；先证明装配与执行无回退，再用固定输入隔离 Prompt/上下文因素、API 因素，分别比较首轮质量和修复保真。语义遗漏在首次程序就存在的情况不得误归因于修复，未完成独立核算、内容及 Evidence 验收不得进入后续架构扩展。
