# Runtime 分析程序连续构建设计与可行性复核

日期：2026-09-03。

状态：**调研及代码复核后的方案草案，尚未实施，也未证明业务效果优于基线。**

直接比较基线：`release/V1.08.01.00-C` 已提交的 `be9d3fd7bbaf81ce354459425a85d41078799e40`。
实现评估同时读取当前待提交代码；不把待提交功能误算为基线原有能力。
本轮仅编写设计文档，不修改产品代码、不调用业务模型、不连接回归数据库、不恢复暂停的回归。

## 1. 要解决的问题和判断

目标不是让模型多写思考文字，也不是给每个错误增加 helper 或校验。
目标是让同一 Runtime 围绕同一个用户问题，逐步取得依据、作出和修正选择、构建和验证同一份
Python 程序，最终交付独立可重跑、有业务解释和表达力的洞察结果。

目前不能由“完整 Schema + 一段分析方法 Prompt + 可重试执行器”推出业务计算可靠。
缺少的是中间的可操作支撑：模型理解了要求以后，如何稳定地把它变成代码，并在付出完整报告
生成和正式查询成本以前发现局部问题。

可行性结论分开表述：

1. **架构可行**：当前已有同一 ReAct、完整事实、独立 Python 执行、源码补丁、澄清和后置 Evidence，
   不必更换框架或重新拆出 Query/Metric/Report Stage。
2. **不是小改 Prompt**：现有编辑协议只服务于失败执行，不能直接承担程序草稿、局部验证和版本化工作记录。
3. **准确性有局部可证明的提升机制**：参数保真、事实无损、确定的数学运算、版本一致性可以独立验证。
   业务定义选择、代理与根因判断、叙事质量仍需真实评测，不能由工具正确推导模型必然正确。
4. **性能收益有条件**：新增构建动作必须减少整份代码重写和正式查询重跑；简单任务不得被固定增加规划调用。
5. **小模型是评测维度，不是保证**：减少单次判断的隐含前提和机械工作有合理依据，但资料和本地审查都不保证
   任意小模型在任意领域达到同样准确率。

### 2.1 调研没有证明什么

- 多几个工具或多轮推理本身不保证数学和业务含义正确。
- 相同 Agent 不自动意味着没有上下文断裂；错误的摘要、版本引用和隐式执行状态仍会断裂。
- Notebook 的中间变量可复用，不等于独立代码可重跑。本项目不能依赖该前提。
- 更强模型上的代码 Agent 成功，不能直接证明当前模型或小模型达到验收。
- Data Formulator 的数据探索与图表工作流有借鉴价值，但它不是本项目所有数据源和单一正式脚本要求的现成答案。

### 3.1 最近失败与拟议机制的关系

`current-r17` 有足够信息但仍出现：结果别名填错、源字段串用、异单位偏离混排、Probe 数值写死、
候选频次替代根因优先级。前两项是代码实现/接口使用问题；后三项包含业务选择与计算组织问题。

程序版本化能减少重写丢失，但不能独自解决这些问题。必须同时有局部可验证计算和明确的业务依据使用方式。
FedQuery 事务异常是独立环境问题；不得通过本方案增加查询重试或改连接逻辑掩盖它。

## 4. 目标架构：围绕一份 Python 程序连续工作

```text
Preparation 的完整事实 + 原问题 + 会话规则 + 调用策略
                         |
                         v
                同一个 Runtime ReAct
          +--------------+----------------+
          |              |                |
       查阅依据       Probe 查证       必要时用户澄清
          |              |                |
          +------> 更新同一工作记录 <------+
                         |
                编辑同一程序的版本
                         |
                可选的局部实现检查
                         |
                 修订理解或代码
                         |
        提交一份完整 Python，在全新执行环境运行
                         |
              正式执行失败回到同一循环
                         |
             成功产物 -> 后置 Evidence
```

上图不是固定顺序流程。简单任务仍可直接完整提交；可以先查证后写代码，也可以写出函数后再查证。
没有“填完所有判断项目才能继续”的本地业务门槛；不增加固定 Brief、MetricSpec、ReportSpec 或另一位审核模型。

### 4.1 两类状态不得混淆

**技术状态**可严格约束：程序 revision、source hash、动作 ID、当前 task、查询成功/空集/失败、
检查针对哪个版本、执行是否保存。这些是避免错误重放的确定性条件。

**业务工作记录**是当前模型的选择及依据，可以修订：统计对象、采用的定义、重要假设、待确认问题、
下一项工作。它不先验正确，不是业务事实本身，不是独立阶段定稿的指标目录。

保持原始用户问题、规则和已查证事实可直接访问。记录出现冲突时，模型回到依据判断；
不通过解析两段自然语言做一致性强校验，不让一个本地 `ready=true` 声称语义已完备。

## 5. 工作状态和存储设计

### 5.1 程序而不是业务大对象作为中心

建议一个任务只有一个活动程序，具有不可变版本。首版可以是业务未写完的普通 Python，
例如只有常量和纯函数；不要求提前构造空章节、空图表或调用 `save_analysis_result`。
编辑存储不把语法通过当门槛：未闭合的源码也可保存并返回语法诊断，但不能执行。
语法不完整时只提供文本行定位，不伪造函数索引；检查和正式提交分别处理其各自的可执行要求。

最小版本信息：

```text
task_id, revision_id, parent_revision_id, source_hash, source_text,
change_summary, working_notes, created_by_tool_call_id, created_at
```

`working_notes` 是可选的少量具名记录：`id / text / basis_refs / supersedes`。
仅记录需要跨动作保留的选择、限制和后续工作，不要求输出内部推理过程，不按每个指标登记。
来源引用指向现有 Schema 路径、用户消息/澄清项、task 内 QuerySnapshot 或检查记录。
本地只检查引用存在且属于当前授权范围，不由引用存在推导“判断正确”。

不另建业务关系图、Metric 注册表、报告槽位表；原 Preparation 和源码继续是各自事实来源。

### 5.2 持久化落点

- 新建单一用途的程序版本表，不能复用 `InsightNsExecution` 存未执行草稿。
- 当前 `InsightAnalysisTask` 增加活动 revision 的技术引用，以原子比较交换更新；不另建通用 Workspace
  或程序头管理服务。程序版本表增加 task/版本唯一性及 task/tool_call_id 幂等约束。
- 更新使用 `expected_revision_id` 比较交换；相同 task/tool_call_id 幂等，旧版本编辑返回冲突而非覆盖。
- 工具观察与检查结果沿现有 `InsightNsMessage.content_json` 持久化，明确关联 task、revision/hash。
  不利用 conversation 级 memory 作为不同刷新任务共享的可变草稿。
- 每个版本保存完整代码，delta 用于交互而非唯一持久化依据；删除历史消息后仍能读取选定源码版本。
- 未提交执行的 revision 不进入历史报告、不增加 Probe/no_data 次数、不触发 Evidence 或本地任务可运行状态。

任务范围读取需校验 namespace、conversation、turn、task 和用户授权。
当前失败补丁读取只在函数内查会话/轮次；新版本接口必须显式补上 task 隔离，不能凭整数 ID 复用。

### 5.3 修订与依据有效性

源码修改产生新 hash，旧检查保留但标为“针对旧版本”；首版不尝试通过复杂依赖图自动证明检查可复用。
用户修改统计范围或定义后，仍可保留程序作为编辑起点，但旧数据观察不是新范围的正式计算结果。
笔记修改不自动改 SQL 或报告，模型必须修改实际代码；正式执行的真实参数和快照才决定最终发生的计算。

## 6. 少量程序操作，不扩展成指标工具目录

名称为设计接口草案，当前代码尚不存在以下三个工具。现有直接提交、Probe、参考及澄清路径继续保留。

| 动作 | 输入核心 | 返回核心 | 明确不做 |
| --- | --- | --- | --- |
| `update_analysis_program` | 首次源码，或 expected revision + 非重叠 edits；可选工作记录变更 | 新 revision/hash、变更摘要、语法诊断 | 不查询数据、不创建正式 execution、不判断业务是否完备 |
| `read_analysis_work` | 当前任务内 revision、源码范围或观察引用；支持批量 | 原文源码、工作记录或真实观察；明确来源 | 不重新选源、不摘要替换知识、不读取其他任务或任意本地路径 |
| `check_analysis_program` | revision、检查种类、可选测试入口及合成用例 | 按版本标记的检查结果、错误位置、适用范围 | 不生成业务结论、不发布报告、不把检查通过当整体验收 |
| 现有 `submit_analysis_program` 扩展 | 完整 code 或 revision 二选一 | 现有正式执行结果/反馈 | 不让模型再次复制整份已保存源码；不把草稿检查当正式执行 |

首次简单提交不需要先保存草稿。后端解析 code/revision 后统一进入现有执行底座，不建立两套正式分析流程。

编辑协议需要明确插入/替换/删除及原版本坐标，不继续依赖失败定位的 `allowed_ranges`。
复用既有行坐标经验，但将纯文本版本编辑与失败程序语法修复门槛分开；不能直接复用会拒绝未闭合草稿的函数。
技术修复仍可从失败 execution 开始；解析到完整程序后转为同一种源码版本，不丢掉原错误及来源范围。
合法全量改写仍允许，不能因编辑便利而禁止模型重新设计必要的计算。

一次更新可以同时保存源码和简短工作记录，不强迫多一次“记录思路”的工具回合。
不并发编辑同一个活动版本。读取、检查和提交返回明确 revision，避免最后检查的是 A、实际运行的是 B。

## 7. 语义细化如何落实，而不成为前置指标计划

这里定义的是模型解决问题时可使用的判断方法，不是必填 JSON 或新的 Stage。

| 判断工作 | 所需依据 | 系统帮助完成的部分 | 必须留给模型/用户的部分 |
| --- | --- | --- | --- |
| 确定要解释什么 | 原问题、会话规则、开放式业务方向 | 保留原文和指代关系 | 洞察重点、解释深度、报告组织 |
| 确定统计对象/范围 | 字段定义、唯一键、业务周期规则 | 明确字段所属来源和关系方向；已有参数原值交付 | 用户没定义的业务周期不能自动猜为某月/全年 |
| 查证技术未知 | Schema、真实 Probe | 真实枚举、列、格式、覆盖、键重复和查询状态 | 观测不等于业务分类或因果证明 |
| 实现数学口径 | 已选对象、单位、明确公式 | 可组合的去重、比率、差异和边界距离运算 | 分母、权重、单位含义、适用公式的业务选择 |
| 解释证据 | 实际计算、总体、局限 | 一致地复用同一计算值与排序结果 | 相关与因果、建议优先级、代理信息是否足够 |
| 写成可重跑报告 | 当前程序的真实计算变量及分支 | 表格/图表结构、格式化、程序局部检查 | 文字、章节、图表选择和事实支持建议 |

某一步不确定，可以回查前面的依据和修订代码，不需要重跑其他语义阶段。
已有明确事实不能被可选笔记降级；也不能把笔记中的假设升级成 Schema 权威规则。

### 7.1 第一批计算能力候选

先审视 pandas/现有 helper 是否已经足够。优先封装反复出现且数学含义明确的组合，不重写基础统计库。
函数接收普通标量、Series 或 DataFrame，返回普通数值/具名结果；不要求 Metric ID、Evidence ID 或注册流程。

| 能力候选 | 明确语义 | 必须测试的边界 | 不承诺解决 |
| --- | --- | --- | --- |
| 对象集合计数和覆盖 | 主体键去重，覆盖为主体与辅助键交集 | 重复明细、孤立键、空主体、空值/复合键 | 从字段名自动识别哪个实体是总体 |
| 差异比较 | 绝对差、相对变化、百分点差各有明确操作 | 零分母、负基数、ratio 与 percent 表示、缺失/无穷值 | 自动决定用户要百分点还是相对增幅 |
| 边界偏离 | 指定下限/上限下的越界距离；标准化分母必须显式 | 下侧符号、区间内、单侧界限、零宽度、缺失单位 | 无依据地选标准化算法或比较不同物理量 |
| 排名及对照 | 排序、并列、与下一项差值/份额的事实 | 并列、单对象、零/负总量、缺失值 | 将频次排名解释为根因优先级或设置风险阈值 |

跨单位的绝对量不能由 helper 默默混排；若已选择有效无量纲口径，可按明确口径计算。
类型和数学前提错误可以返回精确错误；缺业务定义则返回未确定/不可计算状态，不补零、不假定分母。
这不是新的一套全局语义校验，合法自定义算法仍可直接写 Python。

这些 helper 必须同时有：真实签名、返回结构、适用条件、独立预期值测试、可查阅组合用法。
只增加文档而没有可靠执行，或只实现函数却让模型自己猜怎么组合，都不算完成。

### 7.2 计算能力与 Evidence 必须一起闭合

新 helper 的函数调用不能成为后置 Evidence 看不见的黑盒。每个 helper 的实现、输入到输出计算含义及
边界必须可由后置编译器查阅；必要时增加小型操作描述，但不让正式模型编写 Evidence 元数据。

同一实现供运行与解释参考，不人工维护另一套可能颠倒分子分母的公式。
需要验证：普通 Python 写法和 helper 写法得到同等 Evidence 边界；不同总体/参数/单位不误合并；
重复展示同一个计算可以复用定义。图表/表格仍按序列/指标列而不是逐值创建定义。
正式代码、实际 QuerySnapshot 和输出仍是后置事实依据；工作记录、合成测试及 Probe 数值不是正式 Evidence。

## 8. 局部验证的明确边界

### 8.1 两种检查，不新造一次正式分析

1. **源码机械检查**：语法、可确定的函数签名、版本/引用；草稿缺图表、报告和保存调用不是错误。
   不运行当前 `_validate_generated_code_contract` 全量正式检查，否则会再次逼模型先写半成品报告。
2. **可选纯计算检查**：对当前程序中可测试的纯函数，用小型合成输入执行，检查单位、符号、并列、零值、
   去重及分支。结果归属于该 revision，不查询业务库、不读取正式业务文件、不发布产物。

纯计算检查建议针对按常规 `if __name__ == '__main__'` 隔离入口的模块执行测试脚本。
该组织是使用此检查能力的条件，不是所有正式代码的强制模板。测试直接调用草稿中的函数，
不能让模型复制一份“差不多的实现”去测另一份代码。

不建设能穷尽任意 Python 的 AST 程序切片器。模块有顶层查询或依赖不可隔离时，返回
`not_applicable` 及明确原因，保留完整正式执行路径，不判定算法错误，不要求为了检查通过无限重构。
检查无法覆盖的内容必须明示；不能把“未检查”显示为成功。

### 8.2 检查不能自证正确

系统 helper 的预期结果由独立测试给出。模型生成的测试可以发现实现不一致，但可能同时采用错误公式，
因此不能当作业务金标准。权威业务定义或用户答案缺失时，测试无法制造它。

不新增成功后 LLM 阻断审核，不对报告文本逐句强行规定指标，不通过局部测试评分触发业务重试。
检查结果回到同一模型，模型决定修改、查证、澄清或继续完整执行。

### 8.3 安全和工程门槛

当前子进程和允许 helper 的 namespace 不是完备安全沙箱，不能据此宣称任意测试代码已隔离网络和文件。
新检查进程必须不注入 JWT、平台凭据、数据库连接及保存接口，并验证资源/超时/取消清理。
限制 helpers 不足以阻止任意 import 或直接网络访问；真正的无网络执行需要现有执行策略可实现的隔离措施。

因此落地先做源码检查和系统 helper 测试；任意模型测试脚本的执行，必须在隔离门槛验证后开放。
隔离没有解决时，明确保留为未完成能力，不把它偷偷转到 Probe 或带凭据的正式执行器。

## 9. 上下文与连续性

### 9.1 固定事实与动态工作信息

- 原问题、会话指令、选定来源完整 Schema、知识定义、关系状态和调用策略仍为必要上下文。
- 核心协议首次可用，完整参考可查阅；关系/时序/文件及跨源能力取并集。
- 工作记录强调当前选择及原始依据，不重新总结成一份比原事实更有权威的语义契约。
- 源码只有一个活动版本；新动作通常发送修改部分，不要求模型重新输出已经正确的全部代码。
- 真实 Probe 与执行观察按 task/query/revision 标识保存；原始结果可读取，不用笔记冒充查询观察。

### 9.2 分两步改善上下文，不能一次替换历史

首批保留当前原始 ReAct transcript，不同时更换消息压缩策略。先验证版本化增量构建是否有效。
工具回执不重复整份源码和完整快照，只返回 revision、改动及必要诊断，原文可读取。

随后单独验证一种确定性的工作视图：当前源码只呈现一份，旧版源码体可引用已持久化的精确版本；
保留每次动作的关联、真实结果和当前错误。不能产生没有对应调用的 ToolMessage，也不能伪造历史模型输出。
完整 transcript 仍留存可重放；新视图必须通过实际模型供应商的消息协议和澄清恢复测试。

这一步不是让另一个 LLM 压缩分析思路，也不是默默丢弃旧版本。若不能保证可恢复和调用配对，
保持原始历史，不以性能为理由剪裁事实。超出实际模型窗口应明确报告容量问题，不能删除来源或规则。

### 9.3 性能账必须包含新增回合

设完整固定事实成本为 B，初始协议为 K，每次动作/观察为 D_i。n 次模型调用的输入成本至少包含 n * B；
因此增加调用一定有固定成本，不会因“流式积累”自动降低。这里的流式是工作信息连续积累，
不是改模型 HTTP 为 SSE，也不是向用户暴露内部推理流。

可能的收益来自：少重写整份长程序、少重新解释相同错误、在正式查询前修正可测的计算、少执行失败查询。
必须同时记录：总调用、总 input/output token、源码生成量、正式查询次数、最终耗时及质量。
草稿失败和检查失败单独计数，不能把错误挪到正式提交以前，就声称“一次成功率提高”。

## 10. 正式执行、澄清、重跑和终止

- 最终提交绑定具体 revision，后端读取完整源码，使用现有独立 worker，从头获取本次权威数据。
- 不依赖 Probe 样本、之前的 DataFrame、草稿执行缓存或其他任务的变量；本地重跑保存完整源码及原参数机制。
- 草稿中的工作记录、检查代码不成为运行所需的外部文件；最终程序在当前 Runtime helper 环境内独立可运行。
- 只有正式保存成功且现有执行校验完成后，按现有 middleware 终止模型循环，再走后置 Evidence。
- 同轮次澄清挂起时增加活动 revision/工作记录引用；恢复保留原问题、Preparation、观察和用户原始答案。
  禁用澄清的外部工作流不挂起，继续按现有输出策略处理无法确定的情况。
- 取消在模型请求前后、工具动作前后和子进程等待位置检查，不增加定时轮询任务。被取消后不得创建新版本或正式执行。
- 编辑冲突只反馈当前版本；查询基础设施故障保留真实原因，不以重写代码或无限预算恢复掩盖。
- no_data 继续只依据实际查询与必要核实；源码不完整、检查不适用和预算用尽都不是无数据。

## 11. 与旧失败方案的区别

| 旧模式 | 本方案 |
| --- | --- |
| 先产出指标或报告大对象，后续编译成代码 | 直接编辑普通 Python；本地不编译业务语义成报告 |
| 多个阶段分别决定查询、指标和叙事 | 同一 Runtime 持续拥有全部决定和全部依据 |
| Brief/模板定稿后，第二阶段照着实现 | 可选工作记录始终可修订，不是上下游硬合同 |
| 先让完整代码失败，再允许修改 | 正式提交前也能保存、修改、做适用的局部检查 |
| 长期解释器变量隐式承接分析 | 保存源码和事实，不保存可替代正式查询的运行状态 |
| 为了稳定要求模型全用 Metric API | 少量可选数学组合；普通 Python/pandas 和原产物自由度保留 |
| 事后用第二个模型强判报告对错 | 不新增审核者；确定计算独立验证，业务验收依然检查真实结果 |

未来能否拆节点取决于同一程序版本、完整事实和连续恢复是否仍成立，不取决于节点名称。
本轮没有拆节点的收益依据，先在现有 ReAct 工具层落实。

## 12. 落地计划和工程量

整体是中等偏大的 Runtime 增量，不是一次 Prompt 重写。风险主要在草稿/执行状态隔离、局部检查安全、
消息恢复，以及计算 helper 对 Evidence 的可解释性。按以下批次推进，不同时换模型、选源和后置策略。

| 批次 | 范围/主要代码落点 | 完成门槛 |
| --- | --- | --- |
| A. 固定设计和测试底稿 | 本文；现有失败程序、能力表、回归矩阵 | 区分基线/现有修复/新实验；每个机制有目标错误族和反例，不先开新回归碰问题 |
| B. 程序版本与编辑 | 新 `analysis_program_service.py` / `runtime_program.py`；model/migration；tools/agent 注册 | 直接提交与 revision 提交共用正式入口；原子编辑、跨任务隔离、幂等、取消、澄清恢复、草稿不污染 execution |
| C. 少量可靠计算 | 新 `utils/analysis_calculations.py` 或现有合适模块；registry/docs；后置 Evidence 适配 | 去重、差异、偏离能力有独立数值测试，普通 Python 同样可用；Evidence 不因封装丢失边界 |
| D. 局部检查和组合用法 | 程序检查服务、执行隔离、参考示例 | 语法与正式契约区分；合成测试直接对应当前源码；不支持不误报；无凭据/网络和资源边界通过后才开放测试脚本 |
| E. 同一任务上下文承接 | invoker/context/消息持久化、clarification resume | 当前版本、原事实、选择及观察连续；先不压缩 transcript，随后单独对照确定性版本引用视图 |
| F. 验收 | 本地离线行为 -> 固定输入模型对照 -> 真实端到端 | 先达到下节门槛，FedQuery 恢复且用户允许后再顺序回归空间会话 |

不顺带清理 `tools.py` 全文件，不更换网关传输/连接池，不改 Selection/Business Context 职责。
既有同轮次澄清、外部调用、后置 Evidence、任务和前端需求独立保留；当前 `.env` 不参与源码实验回退。

### 12.1 最小实验和停止条件

首个可比较实现至少包含版本化编辑、事实/工作记录承接、直接提交，以及一组独立验证的计算能力。
只有持久化草稿、不补计算支撑，不能宣称已经解决本轮设计目标。

先比较：当前工作区 vs 只增加程序连续构建；再单独加入计算能力。两者均不强制先规划或先 Probe。
候选机制每次只变一个可归因因素，固定 Preparation、问题、模型、数据期间与调用策略。
未明确“本周期”的原问题另列澄清验收，不为了便于比较在产品代码中默认改成某个月。

同一错误族两个有边界的候选实验都无改善，或增量构建只增加回合却不减少业务错误/重写，停止扩展，
重审该机制；不能用增加检查、长 Prompt 或更多回归轮次掩盖。移除只针对实验增量，不整体回滚已有需求。

## 13. 验收标准

### 13.1 离线确定性门槛

- 同一问题：完整直接提交和逐步编辑后提交，最终保存并执行的源码可核对一致。
- 编辑失败不覆盖原版本；并发旧 revision、重复工具请求、跨 task 读取均有反例。
- 草稿不产生假 execution、no_data、Evidence、is_runnable 或前端分析结果。
- 全新进程只依赖最终 Python 和 Runtime helper，即可在参数变化后独立重跑。
- 合成用例覆盖一对多重复、孤立键、零分母、负值、上下侧偏离、单位不可比、并列和缺失。
- 对参数 A/B，两种数据下结论应变化的程序确实变化；没有硬编码 Probe 数值冒充动态结果。
- 澄清前后源码/事实/用户原话不丢失；禁用模式、standard/text/json、取消和后置隔离不回退。
- helper 与普通 Python 的 Evidence 计算边界、公式、单位及 ref 通过等价检查。

### 13.2 模型与业务门槛

- 固定 Preparation 先隔离 Runtime；原问题输入、首次草稿、首份正式程序及每次修订全部记录。
- 正确性按独立计算与业务定义核算，不用模型自己的公式再算一遍自证。
- 有歧义时区分可 Probe、可合理解释、必须用户决定；不能为了“准确”让所有问题都澄清。
- 内容必须有具体数值支持的发现、比较和业务解释；建议有依据，不把排名或相关性冒充因果。
- 图表/表格可展示、标签可读、无空章节；表现力不低于同题基线，不按统一章节数或长度验收。
- 标准输出的 Evidence 全部真实计算位置与边界符合既定要求，不能只查 complete。
- 关系、文件、时序、混合、多源部分无数据、追问和本地参数重跑均覆盖。API/MinIO 不新增为本轮业务验收目标。
- 现用模型与一个明确选定的小模型分别测试；小模型不通过时不能用现用模型结果代替。
- 总耗时、所有调用/token、数据库请求、正式重试与草稿/检查失败均计入；无错误的简单任务不固定增加模型回合。

先每组至少三次用于筛查随机波动，再按已确认空间矩阵顺序验收；三次不是统计可靠性的证明。
整体通过必须同时满足正确性、表达、可用性、Evidence 和性能，不能通过缩小范围换取通过。

## 14. 本轮结论和待确认项

**建议采用代码中心的连续构建方向，但不把“可实现”写成“已经证明更优”。**
它补的是现有首份完整程序之前缺少工作载体、可靠运算和局部反馈的空白，而不是重新分配洞察语义。

存储已选定任务级活动引用加不可变版本；实施前需要以模块原型确定少量计算接口的参数及未知状态、
纯计算检查的安全隔离。这些不是靠真实业务复跑才能发现的问题，应先以离线反例验证。
模型能否选择正确业务定义、是否愿意使用增量能力、净调用成本和小模型收益，属于必须接受真实否证的假设。

本轮未做这些实现，也未恢复回归。既有实测结论继续以
[2026-09-03 回归记录](runtime-regression-review-20260903.md)为准；已有确定性修复和受保护需求见
[待提交改动边界](runtime-working-tree-change-boundary-20260902.md)。
