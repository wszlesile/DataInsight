## 已确认的实现缺口

1. 精确 Schema reader 在同一 ReAct 图调用内的结果没有进入下一次请求的 canonical 工作区。
   Context 初始化副本没有随工具消息更新，导致系统视图和原始 reader 回答重复加载。
   现在每次请求从本轮工具记录合并精确 Schema，再投影当前依赖。完整审计历史保持不变。
2. 同一来源多次读取只覆盖而不合并字段，会丢失先前字段和引用定义。
   合并逻辑以来源 ID 和字段键替换对应定义，保留其他字段、关系、$defs 和缺失字段诊断。
3. 出站 Schema 视图自行反推最近选字段的动作，可能使用 Probe 的窄范围代替原实现范围。
   出站投影与工具状态改为复用同一生命周期解析结果，Probe 完成恢复父工作的来源和字段。
4. Probe 拦截错误的 error_type 与状态解析使用的值不一致，阻止重复调用反而进入 probe_repair。
   状态解析识别真实 violated_contract，测试使用实际工具返回值，不再只模拟预想错误协议。
5. Probe/implementation 替代 execution.core 时没有承接 Python 注入命名空间说明。
   本轮模型把工具名当作 Python 模块导入。两个执行协议现在复用 core 的同一权威执行环境章节。
6. 成功 Probe 后连显式重新选择工作入口也隐藏了，无法在正式失败前处理新技术未知。
   恢复显式选择入口；Probe 观察自动返回父工作，旧工具调用不能自行重开 Probe。
7. select_runtime_work 对 JSON 字符串形式列表/字典缺少现有 reader 已支持的规范化。
   增加 JSON 解码后仍由原 Pydantic 结构校验，非法结构继续拒绝；真实工具 invoke 测试覆盖。

Schema 原始结果只有在 canonical 视图覆盖当前精确字段时才去重；business_context 和错误诊断不被移除。
不会以字符阈值裁掉 Schema、能力协议或有效观察。

## 状态与出站请求联合复核

之前测试分别证明状态解析和历史裁剪，而没有充分证明二者组合后的模型视图正确。
更严重的是，已有“最近 Probe 动作/观察配对必须保留”规则被后加的 implement 分支覆盖。
这属于实现与验收遗漏，不能归因为模型问题。

| 同一个输入场景 | 状态 | 必须可见 | 入口要求 |
| --- | --- | --- | --- |
| Probe 成功，尚无正式执行 | 恢复父工作 | 最近成功动作/观察对及父材料范围 | 正式执行；显式新焦点可再进入 Probe |
| 正式失败 | repair | 当前程序、最新错误、有效观察 | 正式修复；新技术未知允许显式探测 |
| 多批 Schema 只读取第一批 | 原工作不变 | 已读精确字段、其余依赖索引 | 继续读取保持可用 |
| 同一来源分两次读字段 | 原工作不变 | 合并后定义，不相互覆盖 | 当前依赖完整后可关闭重复读取 |
| 工作选择14个来源 | plan 或所选状态 | 不静默删掉后两个来源 | 工作 ID 清单不施加无关的12个上限 |
