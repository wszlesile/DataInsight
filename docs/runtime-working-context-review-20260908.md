## 主要发现

### P1：工作视图替换了核心协议，但没有等价继承

位置：`runtime_working_context.work_contracts`、`runtime_contract_registry.load_runtime_work_contract_text`、`contracts/execution/implementation.md`。

正式实现与修复把 `execution.core` 替换为独立精简的 `execution.implementation`。完整 core 文件仍存在、可读取，并不等于当前生成代码的请求已经包含必需规则。仅检查拆分文件数量和文本存在性不足以证明能力保留。

实际例证：基线反复明确 `get_analysis_parameters(analysis_parameters_schema["defaults"])`；工作视图只给省略号调用和返回类型。任务 540 的执行 2135 把整个 schema 当 defaults，随后取不到 `target_month`。第一次修复没有修复调用，而是硬编码月份绕过取值，损害可复跑参数语义。

本轮已复用 core 中“查询结果与计算语义”和“保存、修复与安全”两个权威章节，并加内容一致性测试；仍不能认为 API 参数、示例和所有计算规则已经完整继承。下一步应以实际执行 API 为单位逐项建立“状态 → 必需说明 → 可执行示例 → 测试”的映射，而不是继续写新的摘要。

### P1：文件 API 的声明与执行分离，校验通过不证明真实筛选

位置：`tools.query_local_file`、`validate_query_constraints`、`_month_grain_filter_satisfies_time_range`。

新的组合 API 返回完整文件，`filter_expressions` 只是校验说明，并不实际过滤。首次会话 44 的对象形式参数被转成字符串参与校验；修复补充起止边界后校验通过，代码却未过滤 DataFrame。执行 2134 把 1—3 月汇总写成 3 月。

独立源文件核算：3 月销售收入 40,337,834.95 元、毛利 28,405,225.03 元；错误报告使用全文件销售收入 125,966,289 元、毛利 86,814,233.40 元。

现已补充既有 `list[str]` 参数类型的运行时检查，并增加窄而可验证的 `file_filters` 协议（`field/op/value`）。组合文件查询 helper 会在读取后实际执行该筛选；低内存读取逐块执行；同一结构化筛选写入 QuerySnapshot、运行工作记忆及后置 Evidence 操作节点。复杂派生 pandas 条件仍可用 `filter_expressions`，但仍明确为“校验说明 + 代码自行执行”。这关闭了简单字段筛选的声明/执行分离，不能据此宣称任意自定义 pandas 语法都已被验证。

另一个确定错位：协议允许 `.eq('2026-03')`，月份范围验证只识别部分字符串语法，不识别这个等价形式；任务 540 的执行 2136 因此继续重试。此验证函数在 `be9d3fd7` 已存在，是基线遗留漏洞被新 API/示例路径放大，不是所有错误都由新工作记忆产生。

后续必须选择统一的可执行过滤表示，或明确保留“声明校验不等于执行证明”的边界；不能持续用正则补丁声称能验证任意 pandas 程序。若改变 API，普通/分块文件读取、QuerySnapshot 和本地任务重跑必须同时验证。

### P1：Probe 事实存在无恢复入口的固定数量丢弃

位置：`runtime_working_context._compact_probe_ledger`、`_merge_probe_ledgers`、`_compact_query_fact`。

工作视图原先对 observations 使用 32 条、confirmed/unresolved 使用 24 条、projection semantics 使用 24 条切片。随后移除原工具观察正文，并可能移除旧 Probe 调用对。当前没有对应的 Probe 事实按 ID 补载工具。

本地直接复现：40 条独立观察变为 32 条，30 条确认事实变为 24 条。这不是正常去重，也不是由当前焦点选择；会丢失不同查询的有效事实。合并还按内容分别累计 confirmed/unresolved，同一事实从未确认转已确认时不能可靠更新生命周期。

本轮已移除这些固定切片，并对带 `fact_id` 的确认/未确认事实实现同一范围内的替代规则。另一个隐藏的累加源也已关闭：外层 ReAct 恢复提示原先会重复内嵌 Probe ledger 和 Schema 详情；二者现作为 `CustomContext` 的类型化工作记忆，由 Working Context 合并和投影一次。仍需补足“只投影当前依赖后的显式事实读取索引”，不能把现有无截断实现误判为最终的按需事实加载方案。

已读 Schema 工作区也不再只保存最近固定数量的数据源；以 datasource ID 更新并保留完整工作记忆，当前状态的 `datasource_details` 只投影材料计划和显式读取要求对应的字段。这样把容量控制从“丢弃旧事实”转成“只装载当前任务实际依赖”。

### P2：工作计划主要管理材料，不等于减少了分析判断负担

位置：`RuntimeMaterialPlanInput`、`resolve_effective_work`、`build_working_request`。

初始 understand 必须调用选工作工具，再进入 plan；计划只组织事实/字段/关系。正式 implement 仍一次编写参数、查询、计算、判断、图表、表格和报告。按需加载是实际存在的，但“已计划材料”不能作为“已解决分析方法”的证据。

计划节点原先禁止读取 Schema 详情工具，却要选择精确字段；后续可补载，但错误选择的修正成本转移给实现阶段。现已仅向 `plan` 工作状态开放 `read_runtime_datasource_context`：计划可以核实字段公式、枚举、格式和关系含义，再提交材料计划；仍不能 Probe 或执行代码。简单文件分析也要经过同一必经链路。会话 45 无代码重试，约 99 秒，但未有同配置基线耗时对照，不能据此证明性能提升。

收敛方向不是新增报告模板 stage 或提前冻结指标。应让本地可确定的工作准备自动完成，让模型调用承载确有信息增量的决策；保留统一程序及同一 ReAct 的修订能力。

### P2：类型化记忆已实现，但失效和替代规则仍不完整

位置：`project_history`、`resolve_work`、`resolve_work_material_scope`。

正向部分：原审计历史不变，出站视图去掉旧程序正文、重复参考正文及部分旧错误上下文，保留最新程序。

仍有风险：旧 assistant 分析文字、旧错误说明及 diagnostics 继续保留；最末次参考读取覆盖之前参考选择，不是按当前代码依赖判定有效期；材料计划长期优先，后续具体读取不更新计划。这些不等于全部错误，但不能把“有类型标记”当成已完成依赖/失效管理。

已修复的真实退化：移除最新 Probe 调用/结果对后，旧选工作消息成为模型可见的最近动作，出现反复 Probe。现在保留最新对直到新的执行替代；会话 43 后一次只有一个 Probe。尚需跨场景验证，不能改成强制所有问题只能 Probe 一次。

### P2：技术修复成功不代表分析逻辑保持正确

会话 43 执行 2131：报警率倍数低于 1 被写成强正向关联；多批次分散报警被认定连续漂移，未建立时间连续性。这些在初版程序就存在。修复时又把缺失高报警组写成 0。两类根因必须区分，不能只补一个终态审计或继续加禁止句。

原基线也依赖模型推理，不能保证所有语义正确；但基线的统计判断边界、实际条件求值及缺失值语义不应在拆分中降级。应先恢复这些必需输入及修复时的程序依赖，再验证是否仍有方法/数据语义不清需要澄清。

## 本轮其他通用修复

- 内层数值聚合经子查询/CTE 到外层 MIN/MAX 的类型传播：使用 SQLGlot 限域类型推导。只确定为数值才规范化，不修改 SQL、不按名称猜测，不把推导失败变成查询拒绝。

- 参数别名与 `code` 使用相同的程序版本生命周期；Probe/正式工具误用反馈切换到匹配工作状态。
- 这些局部修复保留；不能替代上面的整体设计缺口修复。
