## 1. 我们实际在推进什么

目标是形成一个能够稳定交付可信洞察的代码生成与执行型 Agent：完整理解用户问题，保留合法分析范围，真实查询，正确计算，按真实结果组织报告、图表和表格，并能解释数值来源、追问和无模型本地重跑。

当前主线已经从查询接入与流程打通，推进到 **语义定义、实际计算、结果解释的一致性**。与此同时，仍需收敛修复成本及后置 Evidence 的不稳定耗时。执行成功、协议通过、Evidence complete 都只是各自边界内的结果，不能替代业务验收。

保留统一 Runtime 的语义所有权、同一 ReAct 内的 Probe/修复、动态报告、同轮次澄清、多源和外部输出能力。下一步不应通过缩减选源、冻结报告模板、业务关键词门控或执行后 Review 获得表面通过。

## 2. 当前项目架构

| 层次 | 主要落点 | 实际职责与边界 |
| --- | --- | --- |
| 交互与入口 | `frontend/src`、`src/controller` | 会话交互、数据源绑定、报告/图表展示、Evidence 查看、工作流与任务入口 |
| 会话与任务编排 | `src/service`、`src/agent/invoker.py`、`src/insight_task` | 轮次/执行/产物持久化、SSE、任务调度与取消、澄清恢复、模型调用及本地重跑 |
| Preparation | `src/agent/analysis_preparation.py` | Intent、数据源选择、字段语义与关系补充、必要 Schema Probe；交付完整已选 Schema 和问题覆盖 |
| Runtime 工作状态 | `runtime_driver_state.py`、`runtime_working_context.py`、`runtime_workspace.py` | 同一 Agent 内的 understand → plan → implement；按需进入 Probe、修复、澄清；保存可修订语义对象、材料计划、当前程序和观察 |
| Runtime 工具与执行 | `src/agent/tools.py`、`src/analysis_runtime` | 查询约束/API 校验、真实执行、QuerySnapshot、技术修复、参数与产物保存；确定性计算及局部表达 |
| 后置证据 | `post_analysis_evidence_service.py`、`evidence_assembly_service.py` | 从成功代码、查询事实和产物编译计算边界及引用；结构化产物本地处理，剩余正文候选有界模型消歧 |
| 本地重跑 | `analysis_execution_rerun_service.py`、`analysis_runtime/executor.py` | 从执行快照重跑同一完整程序与参数，不重新调用模型 |

语义规划与材料规划是同一 Runtime 内的工作，不是新建两个分析 Agent。前者确定总体、粒度、算法与判断依据，后者组织读取和探测依赖。Python 仍完整拥有查询、计算和动态交付。

这个职责方向合理。当前最薄弱的边界是：计划主要是模型可读的定义，实际 Python 可以另外选择算法；局部表达函数可以正确，旁边正文和建议仍可另写一套解释。当前后端结构校验不认证这两种语义一致性。

对 4164 的额外核对：正文收入 40,337,834.95 元、成本 7,986,588.54 元、毛利 28,405,225.03 元。源码显示毛利直接来自利润表，成本另按单位成本重算；两者没有形成同一核算边界，也没有解释差异。这不是仅靠减法就能判定哪个值错，但足以确认不能把三者当同口径利润闭环展示。成本利润率还混用该重算成本作为分母；`mean()` 生成的产品比率均值与总体比率也必须分别命名。

从轨迹可确认三个不同问题：

1. **计划本身**：总体、输入粒度、分类成员、分组和判据可能未定义准确，工具结构合格不等于计划正确。
2. **计算实现**：完整分布被极值子集替代，变动单价被 first 折叠，事实/结果身份可读仍不保证算法实际按定义实现。
3. **结果解释**：计算及局部数学表达正确时，周围正文/建议仍是与结果无关的静态业务推断。

## 5. 下一步推进顺序

### A. 先固定评测与对照，不继续扩张计划协议

用已有 45/65 隔离入口固定问题、完整 Schema、当前真实契约、一个人工核对过的最小语义计划、数据及模型配置。人工核对必须清理分析标题中的预设评价、粒度冲突和缺失依赖；局部改对几项不能命名为“完整正确计划”。

分别评分计划质量、程序计算、正文解释。保留正式静态检查和真实保存/图表验证；Worker success、旁路捕获正文和正式提交成功分开记录。下一次小批试验重复独立生成，不能把同一程序四个数据变体当四次模型成功。

最小首轮建议三次独立生成，每份程序执行全相等、部分并列、唯一最大、单项及空集；这只是发现机制缺口的门槛，不是统计稳态证明。未通过就定位最早错误边界，不立即铺开全链路批量复跑。

### B. 优先验证“同一计算结果驱动整段解释”

保留当前默认事实表达进展，在现有 Python 动态报告能力内验证：完整计算结果保留到比较阶段，数学状态在一次求值中形成；正文各处引用同一结果，建议由该结果和有出处的判据共同决定。新的发现需要修订原语义计划，不能在实现里凭标题补判据。

事实比较可使用确定性表达，业务解释仍由 Agent 结合规则选择，不将整份报告替换成固定模板。没有规则时仍可以报告规模、分布、差异及变化，解释能说明什么、尚需什么信息；不能把可计算条件当作健康或风险标准。

本轮先不新增 `result_extent` 等用途属性、不新增相近 API、不强制函数名、不增加执行后模型审查。已有试验说明这些办法没有稳定改变行为。任何新设计都必须证明周围正文和建议随数据变化，而非只证明函数被调用。

**通过条件**：各变体事实与独立统计一致；所有结果相关结论和建议同步改变；单项无多对象断言，零命中不继续建议优先处理命中类别；有实际业务规则时能作有效评价，缺规则时不冒充已确认。报告仍完整回答问题、保留图表表格和业务价值。

### C. 独立收敛 44/64 的粒度与核算口径

先按源 Schema、记录和业务定义确认成本究竟是销售结转成本还是生产成本；确认公司/车间/产线/产品/月的连接基数与单价变动。需要金额时，按真实细粒度与适用数量求值后聚合；不把生产单位成本直接乘销量当默认正确算法。没有适用数量或规则时明确未确定范围。

固定独立核算结果，验证关联前后可加量不被重复、非可加量的加权依据可说明、毛利与成本口径相容或差异明确。成本结构问题必须交付实际构成数据及比较，不能只输出“建议分析成本构成”。这是第二个主阻塞，设备极值通过不能代表它通过。

### D. Evidence 与技术修复继续做有界独立验证

用同一保存程序和产物编译，区分确定性血缘覆盖与正文候选消歧。检验默认表达中的项数/极值边界、日期/维度排除、重复展示绑定及 resolver 当前值/单位/来源；三个剩余候选需要真实分类，不能为 complete 直接删掉。

先分类耗时来源，再决定优化：结构化槽应本地绑定，真正非结构化语义允许有界模型帮助；补漏只修同一计算边界的未解决位置。当前“一个候选也可耗时几十秒”的问题不能用无限重试或扩大模型超时消解。

技术修复复用已保存错误请求，证明一次修复能保持完整语句输出和非错误逻辑；将范围选择失败、替换内容失败、算法变化分开评估。不要因完整重写最终成功就宣称局部修复有效。

### E. 局部实验通过后，再做完整串行回归

先 45/65、44/64，随后覆盖 43/63、46/67、47/48 的当前有效轮次及多源/Probe/澄清/无数据/外部输出/本地参数重跑。选源 provider 按产品配置，必要时做可比 local/semantic 对照。

每例记录 Preparation、Runtime 和 Evidence 分阶段时间、生成/纠正/Probe/正式执行/修复次数、核心指标独立核算、报告深度、结构化产物和引用点击。当前没有本次确认的统一秒数 SLA，不把 38 秒隔离实现耗时或 1 秒本地编译冒充端到端性能达标；性能需按相同环境、模型、问题和数据对照基线。

### 新发现的上游语义边界

冻结输入的字段定义虽然正确给出安装日期的 string 类型和样例，但已有 `semantic_enrichment` 将它补成“设备投入使用的日期”，并标记 `confidence=confirmed`。这与本次核对计划中安装日期不等于投产日期的解释存在冲突。不能认为类型完整就表示业务语义正确，也不能将人工核对计划视为已修复输入中所有旧补全。
