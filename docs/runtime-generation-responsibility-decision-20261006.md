# Runtime 初次生成职责决定

日期：2026-10-06。范围：当前未提交代码及已保留的正式生成筛查，不修改历史样本，不新增模型调用或重试。

## 决定

停止把“结果身份必填、绑定检查、语义检查后重试”作为准确性收敛路线。上一轮提出的“让身份与判断依据成为可检查提交内容”不足以解决首次生成的错误，本决定收窄并修正该建议。

下一项主线是**减少独立产生算法与判断的责任**：分析意图保存目标、总体、来源和原始业务约束；执行定义一次产生算法与可执行判断；展示消费本次执行结果。现有工具扩展和更多校验不替代这项重构。原生执行和真实消费记录有独立价值，但不得当成自由正文正确性的证明。

这不是已完成的生产重构，也不宣称当前方案已通过完整业务验收。保留任意 Python、自主分析、自由叙事、全部数据源与产物能力；不能通过只输出受支持的模板事实句解决原问题。

## 已核实的冲突，而不是新假设

1. `RuntimeCalculationRule.definition/result_fields` 的代码描述已把算法权威移到正式程序；但 `execution/semantic_planning.md` 仍要求字段公式，并要求 definition 中写成员条件与聚合算法。改一句描述没有改变整项工作要求。
2. `RuntimeDecisionCondition` 仍要求 condition/when_true/otherwise；`semantic_planning.md` 明确要求先写这些条件和表达，`implementation.md` 再要求把它们转换成分支。计划和程序仍是两份判断表达；`semantic_implementation_bindings` 只定位引用，没有执行这份计划。
3. 最新真实样本采用极值 helper 后，正文仍从 `iloc[0]` 写单个最大对象。错误在首次程序内部形成。将源码封存、增加 ID 或确认引用存在都接管不了这个起点。
4. 计划中的 basis/source_references 是模型声明，不是业务规则解释已正确。没有依据的健康、负荷、效率或产能结论不能靠补一个 basis 字段变正确。

因此不采用“将自然语言 condition 编译为另一份 Python 再比较”“检查正文是否提及 ID”“验证用了极值函数”“搜危险业务词”“填入字段后反复重跑”等路线。它们保留了重复语义生成，还增加拒绝和修复成本。

## 执行定义优先的具体边界

分析意图与执行定义不是两份同义计划。前者回答用户想知道什么、输入依据是什么、哪些原始约束必须保留；后者是唯一算法。用户或 Schema 已提供的公式原文必须保存为需求与出处，不能删去真实约束来消除重复。

数学运算使用声明式执行定义，宿主直接求值，而不是让模型再写等价 pandas/SQL 算法。自定义算法保留 Python 函数，源码自身作为定义。执行定义允许探索后增加或改变；不要求进入查询前预枚举全部指标。

对定义的依赖、查询和计算调度，宿主承担确定性工作，包括结果注册和调用顺序。模型不再同时负责算法及其 bookkeeping。绑定由实际定义执行时自然产生，不是成功后根据相同数字、列名或声明补造。

判断的条件只在执行定义中写一次：数学条件直接由运算产生完整比较集合，业务条件使用实际规则及输入；未知依据单独承接事实和未知原因。展示读取保存的判断状态，不再有一份自然语言条件等待第二次翻译。已有 ReportFragment/compose_report 只证明消费，不能阻止自定义展示函数内部写出另一项评价。

自由自然语言仍存在不能机械认证的边界。任意 Python renderer 或回调可能包含错误判断；改名为 commentary、要求 decision_id 或封存源码，都不会消除它。**没有证明解决这一边界前，不将该设计包装成“完整报告准确性已经可由结构保证”。**

## 性能依据及统计边界

最新 `model-screen-r2` 的 system 为 57,042 字符，冻结语义计划 JSON 为 7,394 字符；一个问题包含 9 条计算规则、11 个输出身份、4 条判断定义，condition/when_true/otherwise 合计 480 字符。实际输入 22,926、输出 3,419 tokens，生成 50.391 秒。

调用与 worker 合计 59.781 秒；两者之差 9.390 秒包含 worker 启动、读取、执行及筛查开销，不是 Python 计算 CPU 耗时。该样本没有 fresh Preparation、规划和服务全链路，不能估算线上各阶段占比，也不能将全部耗时归因于上下文长度或模型能力。

这些数据支持先检查生成工作的内容和重复表达，不支持宣称“减少某字段即可提高准确率或延迟”。下一次测量须保持问题、Schema、算法和完整报告范围，统计全部实际调用与 tokens；不得先加一轮模型再把它排除在性能统计之外。

## 实施次序与停止条件

1. 先定义分析意图与可执行定义的分工及旧快照兼容迁移。历史自然语言计划作为需求与来源读入，不自动编译、不视为已证明算法。新入口不再要求生成另一份条件及结论分支说明。
2. 复用现有 worker、原生算子、PythonCalculation、事实和展示消费设施，验证一个完整执行定义能从头生成所有原分析内容，并无模型复跑。不要先增加新持久化层、编译拒绝层或再建一套报告协议。
3. 使用当前设备与成本的全范围需求验证计算、判断及完整正文。包括并列、单项、零命中、缺少业务规则和金额口径变化；不是只核对结果字段是否齐全。
4. 设计如果只是包住旧 Python 或要求更多声明，立即停止。若 renderer 仍能独立产生相反判断，记录为未解决；不得加语义 gate 逼它重试后宣称机制成立。
5. 只有责任重构及手工行为检查形成具体可审视实现，再开展真实完整生成。首个失败样本保留，不对它做专用源码修补或等价提示重试。

## 计算后表达：纠正“同一程序内展示”的歧义

后续 R5 复跑暴露了一个关键的设计缺口：当前 `ExecutablePythonProgram.deliver()` 确实先执行查询和计算、再调用 `present(results, parameters)`，但 `present` 的 Python 源码已由模型在查询前生成。它运行时能读取真实结果，不等于撰写它的模型看过真实结果。R5b 的 2022/2023 并列安装年份仍被报告压成单一年份，正是这个差别的可观察案例。结果 helper 可以正确返回完整并列集合，但无法让预先写好的自由文本自动理解本次集合。

因此“同一 Runtime 在计算后组合表达”必须指**模型作者在计算后实际收到本次事实**，不能只指 Worker 在运行时把结果传给预先生成的 renderer。下一步的主路径应分成同一 Runtime 轮次中的两个生产动作：

1. 模型提交唯一的查询、算法和可执行判断定义；Worker 执行一次，保留完整执行工作区及其已算出的事实、判断状态和已规划产物。这个阶段不接收或保存最终报告，也不重新查询。
2. 同一会话模型收到有界、面向问题的真实结果视图后，撰写自由报告并补齐所需展示；宿主将其与原执行工作区合并并只保存一次。模型是结果表达的生产者，不是审核者。执行后不跑语义评判、报告 gate 或自动语义重写。

结果视图由 Runtime 根据已计划的问题和实际产物构造：小型聚合/分布需包含完整值与并列集合；高基数明细只给有明确截断标记的样本，并提供可由已执行定义直接取得的聚合结果。不能把截断样本伪装成总体。表达阶段只能消费当前执行 ID 的工作区，不得再查数或另造计算口径；超出已有事实且会改变用户所问含义的关键选择，才进入现有同轮澄清判断。

这项拆分会增加一次**必要的表达生成调用**，因此必须把它纳入完整延迟和 token 核算；不能为避免统计成本而宣称预先生成的 renderer 已经看过结果。它不增加语义验证调用或重试。第一步工程工作不是再试提示词，而是验证现有 Runtime 是否能安全承接一个不落库的执行候选：执行 ID 绑定、原始查询/事实工作区可重用、进程故障时清理、并发会话隔离，以及最终单次保存。若现有结果快照不足以恢复展示所需事实，应扩展当前执行快照/worker 生命周期，而不是第二次查询或序列化任意 Python 闭包。

现有代码的可复用点和缺口已核实：`SemanticExecution.trace()` 已将本次 source receipts、事实行值和判断状态转成 JSON；`StructuredResult`/worker 序列化可传递这些 trace；查询无需再次执行即可给模型构造小型事实视图。但 `save_analysis_result()` 强制要求非空最终报告，`execute_python` 成功后立即将 execution record 标成 success 并返回终态 ToolMessage，`reduce_runtime_tool_result()` 同时把 Runtime 置为 `COMPLETED`。因此不能把现有成功消息简单改成“继续写报告”：要显式增加一个**未完成的执行候选生命周期**，将候选及已生成图表/表格绑定到 execution/workspace，第二阶段完成后才落最终报告和 success。失败、取消或会话结束时，候选必须按 TTL 清理；执行历史不能把候选误显示为成功分析结果。

进入模型接线前的设计停止条件：表达调用必须能看到本次全部相关小型事实和已求值判断；大结果视图要明确总体与截断；最终保存前不能有用户可见的半成品；参数复跑重新计算并重新表达；完整报告、图表、表格和 JSON/text 输出范围不缩水；不会因业务文字“可疑”而拒绝或触发重写。任何一项无法由现有执行快照和 Runtime 状态满足，就先补齐这个生命周期设计，不做孤立 helper 或语义门控。

本轮完成的是架构责任审计与取舍；没有新准确性机制准入，没有生产代码变更，没有新增测试通过数或性能提升结论。用户已明确要求不要补丁及无意义语义校验重试，后续以本决定限制推进范围。

## 后续落地：规划输入与旧计划读取分离

用户再次授权继续后，完成第一处责任调整。`RuntimeDecisionIntent` 仅保留判断需求、basis、criterion、source_references 和 supporting_fact_ids；新 `RuntimeSemanticIntentInput` 成为 `plan_runtime_semantics` 的公开输入及当前问题投影。新入口不再请求 condition、when_true、otherwise；没有增加语义验证器、源码门控、重试节点或模型调用。

原 `RuntimeSemanticPlanInput/RuntimeDecisionCondition` 继续承担存储及旧计划读取，完整旧字段仍可接受并保留。新意图通过既有处理器存入同一个 semantic_plan，未新增数据库结构或竞争的计划状态；保存不制造空的旧条件字段。仍使用 decision_conditions 键承接判断需求，是旧快照兼容的容器名称，不代表新入口交付可执行条件。

计算需求、输入来源、粒度、单位、分组、实体身份、未知项及规则原文保留。公开 Schema 仍承接既有 question_id；没有通过减少问题或计算要求来解除执行约束。语义规划及实现契约同步调整，移除规划先写逐字段算法和条件分支、实现再翻译的相互矛盾要求。算法与可执行判断的责任归正式程序。

验证结果：11 个相关文件 **398 项测试、6 个子测试通过（9.23 秒）**。新/旧计划分别经过实际处理器、状态归约、材料计划、Probe、实现及失败后的修复工作视图；新公开工具 Schema 不暴露旧分支字段，旧文本保留。额外验证原始加权公式和业务规则出处在工具解析、保存与 semantic_plan_work_view 中不变。参数复跑约束等现有边界也保留。首次测试失败是契约文字断言所依赖的原短语被同义改写；保留既有事实说明表述后最终相关集合通过，未修改算法或增加校验来迎合测试。

本步没有真实模型、真实文件新验收、历史数据库写入、部署或提交；不将测试通过转换为准确率或性能提升结论。**尚未完成**：正式程序中算法、判断与展示的唯一执行生产路径及宿主调度。旧 mandatory binding 机制未扩大，也未因新入口而撤掉已有交付要求。自由正文仍可能独立写出错误判断，不能宣称本步已解决这一边界。

## 2026-10-08 两阶段表达实测：已见事实仍未收敛

在同一设备分析意图和材料计划上，对当前 `execution.definition -> Worker -> execution.expression` 做一次隔离生成。此筛查不写入分析/报告，不做自动重试，也不执行 Evidence；因此它只验证 Runtime 新职责链及实际模型行为，不代替全链路验收。记录见 `.codex-regression/definition-expression-screen-20261008-r12/`。

- 定义调用 36.328 秒，正式 Worker 2.609 秒，计算后表达 28.453 秒；两次模型调用合计 37,255 tokens（定义 20,726，表达 16,529），无 Probe、无重试。表达不是免费开销，且本次样本不是完整 API 的端到端耗时。
- 计算事实包含安装年份 2019–2023 对应 1、1、2、3、3 台，2022 与 2023 持平；额定功率合计 885 kW、平均 88.5 kW、最大 350 kW、最小 3 kW；状态为 7/2/1，10 家制造商各 1 台。完整分布和执行定义均进入表达输入。
- 报告仍把状态分布称为“运行状态总体良好/设备利用率较高”，将额定功率推成“总能耗”“负荷影响”，从年份计数推断“逐年增长”“产能扩张/设备更新”，并给出维护、采购和排程建议。年份序列明确有平台期；来源并未提供实时功耗、停机原因、维护周期、采购动因或生产流程依据。
- 因而“两阶段让表达作者看见真实计算事实”已由执行路径和输入记录证实，但它没有消除首次生成中的无依据业务解释。通用事实/推断表达指引加入后，该输出仍重复这些错误；该临时指引已撤回，没有保留一轮未见效果的提示堆叠。无语义拒绝、无自动改写、无关键词检查。

本次把失败定位在表达阶段的知识与证据承接，不再归因于分布事实不可见，也不能仅凭来源绑定、事实引用或 complete 状态宣称报告正确。接下来不增加“可疑结论”检查或语义重试；需要先明确一个不缩窄自由叙事、也不把任意解释伪装成被证明事实的通用表达机制。当前运行结果仍不达准确性验收，新增第二次模型调用也带来显著耗时，不能据此批准全量接入或宣称准确性/性能改善。

## 2026-10-08 r13–r15：把权威分层显式化仍未形成可靠行为

随后没有扩展语义 gate，也没有因为不合格输出自动重试。针对来源描述与字段定义混在同一对象中的冲突，将数据源级描述投影为 `dataset_context`（`evidence_authority=context_only`），字段级描述仍留在 Schema；针对空 `decision_conditions` 被表达阶段忽略，将现有语义计划投影为 `expression_scope`，明确标注 `descriptive_only` 或 `planned`。这两项都是既有资料的类型化承接，不推断结论，也不改变查询和能力范围。三组定向测试最终 175 项通过。

三次隔离模型筛查使用同一设备任务，均为定义、一次 Worker、表达两次模型调用；不落分析报告数据库、不执行 Evidence、不自动重试。屏幕报告分别保存在 `.codex-regression/definition-expression-screen-20261008-r13/`、`r14/`、`r15/`：

- r13 仍把“加工设备数量最多”扩大为工厂以机械加工为核心、流程能力完整；把状态比例描述为运维健康；并将额定功率解释成负荷/维护建议。这证明单独把数据集描述标为 context-only，并未解决表达对可观测事实与业务结论的混淆。
- r14 的叙述有所收敛，但仍将加工设备称为核心设备类型，将近年安装数量解释为扩产或更新，并评价运行状态良好。由于模型生成具有随机性，不能把单次文本变化归因于结构标记，也不能据此判为解决。
- r15 在显式提供 `expression_scope.judgment_scope=descriptive_only` 后，仍称整体状态良好、维护比例合理、供应商分散降低风险、近三年投资扩张；把额定功率称为总装机功率，并推断最大功率设备属于核心产线。其分组和基础数字大体正确，但业务评价及因果解释缺乏对应判据和字段依据。
- r15 定义 29.422 秒、Worker 2.687 秒、表达 22.437 秒；两次模型调用共 36,183 tokens（定义 20,632、表达 15,551），无 Probe、无自动重试。r14 为 33.578/2.687/21.594 秒、36,611 tokens；r12 基线为 36.328/2.609/28.453 秒、37,255 tokens。小样本且随机输出，不支持延迟或准确性改善结论；单次必要表达调用自身仍约 22 秒。

这组失败进一步缩小了缺陷范围：表达输入已经同时拥有数据、字段定义、来源用途的低权威标记和“本题只描述事实”的计划边界，系统却仍允许模型用一个自由文本字段一次性生成全部断言。当前只有生成契约，没有让计划中的判断成为正式可执行的判断，也没有让正文的业务评价依赖该判断结果。更具体地说，`semantic_reporting_scope` 只是上下文投影；`compose_analysis_presentation` 校验候选身份和输出形状后接受自由正文，不会、也不应该通过词面或语义审核来修正它。

因此，不能再把增加上下文标签或重复强调描述边界作为主要推进路线。下一项设计审查应沿着既定“执行定义唯一生产算法和判断”的主线检查：当业务判断有明确来源时，它是否确实在执行程序中形成可消费的判断结果；无业务判据时，表达能否清楚保留统计事实并自然说明边界，而不把它伪装成健康、风险或因果结论。若仍要求自由正文独立重建判断，设计就仍有职责缺口。后续改进不能通过事后文本审核/重试实现；也不能简单缩窄叙事为固定模板来制造准确率。该缺口尚未解决，r15 不通过准确性验收，不能以此批准生产全量接入。完整 API 与 Evidence 尚未在本轮运行，隔离屏幕结果不能替代二者。

## 全局契约消歧后的对照复跑：r17 仍未通过

对真实 r15 表达请求核对后，发现同一 system prompt 既要求无依据时只说明事实与边界，又用“完整洞察”“解释业务含义”“报告叙事唯一语义所有者”鼓励模型补充业务解释；开放目标“为业务决策提供基础”也可能被模型当成评价授权。对这些词的职责含义做了收窄：业务含义限于 Schema/用户上下文定义，决策基础不代表授权运营评价，并把表达阶段的 `descriptive_only` 作为当前问题明确范围。没有增加任何输出校验。

先用新的正式定义请求筛查 r16，模型生成的直方图代码在 `pd.DataFrame` 处出现长度 5 对 10 的技术错误，流程按隔离脚本规则停止，不修源码、不重试语义；该次没有进入报告表达，不能用于比较契约效果。为了只检查表达契约，r17 重用 r15 已成功定义的源码及相同本地 Worker 事实，并使用更新后的表达工作视图重新生成。无数据库写入、无 Evidence、无语义审核/自动重试。r17 的定义 29.422 秒、Worker 2.938 秒、表达 27.594 秒；两次模型调用合计 37,000 tokens（定义 20,632；表达 16,368），最终报告 2,826 字。

r17 仍然宣称“可用设备”90%、停机比例较低、状态良好，推断维护例行且不影响生产；把 2019–2023 的计数称为逐步增长，并据此判断产能扩张；把额定功率推成全厂理论耗电负荷、安装功率及设备用途；从制造商分布推出风险降低。已知事实 7/2/1、各年 1/1/2/3/3、10 家各 1 台及额定功率统计大体正确，但关键业务评价仍无依据，准确性依旧不通过。r17 表达段 input 含更新后的全局规则、`expression_scope.descriptive_only` 和完整事实，因此不能把失败归因于边界字段未传入。

结论：消除提示文本的显性矛盾是必要整理，但本次对照已经表明，单靠更清晰的自由文本生成契约仍不能可靠抑制无依据评价。停止继续做同类提示词试探，也不把自然语言正则、另一个 Review Agent、要求模型自证或自动重写当作答案。保留两阶段生命周期（它仍解决计算后表达作者可见真实结果的问题），但不把它或本次提示修订宣称为语义正确性机制。下一项必须回到执行责任设计，明确该分析的“判断”究竟由哪些可执行结果支持；对没有判据的问题，系统要能交付全面、自然的描述性分析，同时不诱导表达模型额外填充经营结论。自由叙事范围要保留，是否能在不做文本语义审核、不降低分析范围、不增加表达模型调用的前提下同时达到这一点，仍未证明。先完成该设计的职责审查，再决定是否值得再跑端到端 API/Evidence；当前隔离筛查尚不足以批准生产推进。

## 可执行决策对象审计

对上述职责边界做了代码核实：`RuntimeDecisionIntent` 会保存 purpose、basis、criterion 和来源引用；`semantic_implementation_bindings` 仅生成路径、mode 和输入映射。`ExecutablePythonProgram` 当前唯一有类型的决策接口是 `register_extrema()`，其谓词固定为数值极值唯一性。其他业务判断只能作为普通 `PythonCalculation` 任意输出，没有独立 decision identity、判据出处、求值状态或表达消费关系；Evidence 也把任意 PythonCalculation 的业务含义标记为 `not_evaluated`。这意味着“正式程序是判断唯一生产者”目前是提示契约，通用业务判断并没有与数学极值对等的执行对象。

这缺口可以解释为什么计划中的业务决策尚不能以统一运行时记录交给表达模型，但**不能**解释 r17：设备计划的 `decision_conditions=[]`，其报告本应是描述性分析；因此即使增加通用决策对象，也不会阻止表达模型在没有计划决策时自行生成结论。不能把增加一个 `DecisionRef` 当作 r17 的修复，也不应仅为增加类型记录而扩大状态模型。

后续实现审查需先回答两个不同问题，再决定是否编码：一是有已声明业务判据的决策，是否需要作为普通事实之外的有类型执行结果，以便表达消费且 Evidence 明确标注“已执行但业务依据未经认证”；二是没有已声明判据时，如何在保留自然叙事及现有分析范围、不增加语义校验/重试的前提下减少表达自行创造评价。当前可证明的边界是：第一项存在可实现的结构缺口；第二项无法由该缺口解决，提示和类型记录都尚未形成可靠行为约束。未找到能同时满足准确性、自由表达、无语义审核和无额外表达调用的机制前，不再堆小型类型或提示修补。

## r18 表达历史投影：确认节省输入，准确性仍未达标

沿着表达职责继续检查 Runtime 请求，发现候选生成后仍将完整 `definition_source` 作为配对 AI tool call 参数重放给表达模型。r17 的 request log 显示表达工作视图有 9,541 个 history tokens，总输入 14,560 tokens；源码已经执行完成，表达只需要语义计划、候选事实和产物，却仍收到约 3.3k tokens 的程序定义。

现已在 `project_history(..., work='express')` 中，仅对状态为 `presentation_pending` 的正式调用，把**出站副本**里的已执行源码替换成短状态说明；配对 tool call 结构、候选 ToolMessage 中的计算事实和图表/表格不变。用户可见/可恢复原始 ReAct transcript 不变；实现和修复状态也继续保留完整源码。测试证明 50k 字符源码不会出现在表达工作视图，候选事实不丢失，且输入历史对象未被修改。

用 r15 完全相同的已成功定义及本地数据做表达对照：表达输入从 14,560 降至 11,936 tokens，下降 18.0%；工作视图从 17,582 降至 14,288 tokens。表达耗时 25.860 秒，对比 r17 的 27.594 秒；单次生成且缓存状态不同，延迟差不能归因于源码裁剪。两个阶段总 token 从 r17 的 37,000 降到 34,046（约 8.0%），定义输入和模型输出任务未变，主要差额来自表达上下文与输出文本变短。该优化已通过相关测试，但还未经过完整 API+Evidence 链路。

r18 报告仍未通过准确性验收：将类型组合扩写为完整生产流程，将“运行中”改写为正常/整体良好，将额定功率解释成装机功率；此前的投资扩张、设备用途猜测有所减少，但只有一个随机样本，不能归因于上下文裁剪。它证明表达模型收到更少无关代码且成本下降，却没有解决无依据评价。记录于 `.codex-regression/definition-expression-screen-20261008-r18/`；无报告数据库写入、无 Evidence、无语义审核/自动重试。

这项改动属于针对生命周期边界的上下文与性能收敛：执行前源码供执行/修复，执行后事实供表达。它既不删减分析内容，也不声称能限制自由正文的语义。剩余准确性问题仍要回到表达输出的生产责任，不能通过继续裁剪历史来掩盖。

## r19 结果契约消歧：有收敛迹象，但仍不验收

审查已加载的 `result.artifacts` 后确认，局部 `expression_scope` 与报告契约仍有措辞张力：开放式报告要求“业务含义”“每个重要判断”，却没有清楚说明事实型结论本身就能满足分析深度。现补充规则：完整分布、最大项/并列和数学变化可直接作为核心结论；事实观察不必再包装成经营评价；健康、风险、流程完整、适用性、原因及行动价值需要已声明判据。没有删除图表/报告范围，也没增加结果语义校验。

用 r15 相同已成功定义和 Worker 事实运行一次新表达，r19 为 11,936 prompt tokens、1,329 completion tokens，表达 19.703 秒；模型/缓存与报告随机性不同，时间和输出长度仅作为样本。相较 r18，报告不再断言运行状态整体良好或产能扩张，更多使用各维度的计数、占比和范围，表现有收敛迹象。但仍把设备类型说成“覆盖完整生产流程”，把安装计数曲线解释为设备更新换代高峰，把额定功率范围说成生产设备完整谱系，并称 30% 类型为“集中度较高”。这些都是数据字段与计数无法推出的业务含义/充分性评价。故准确性仍未通过；本次改善是提示措辞单次样本的行为变化，不证明可靠性提升。

既然 r19 已验证事实型结论的正向表述能减少一部分无依据扩写，而同一请求仍残留业务叙事推断，后续不再对同一个设备样本反复调提示。应改用已有不同真实任务做小型盲化验收矩阵，先由用户原始请求、Schema 和真实计算独立建立事实/判据边界，再仅评价首次生成；不以更多提示轮数或单一案例“越来越像事实”宣告通过。若跨任务仍重复越界，准确性目标在当前“完全自由正文、无输出语义审核、无额外模型调用”约束下尚无已证机制，须报告设计限制，不应启动高耗时全链路重跑或部署。

## 跨任务边界基线：产品成本与利润历史案例

为避免继续只围绕设备描述任务调 prompt，抽取 conversation 56 / turn 87（“分析一下今年3月份的各个产品的成本以及对应的利润”）作为不同任务族的边界样本。它不是当前代码复跑：原始对话详情显示历史执行成功，所选/使用数据源为 182、183；没有改写历史结果。使用留存的两份 CSV 独立筛选 `年月=2026-03` 后，销售和成本各 36 行、各 3 个产品；销售额 40,337,834.95 元、毛利 28,405,225.03 元、总体毛利率约 70.4%。各产品毛利率约 73.85%、65.57%、71.13%，毛利贡献约 36.5%、27.8%、35.7%。

历史报告的汇总算术基本正确，但把 65.57% 称作“亏损边缘/利润空间明显偏薄”，并把恰好覆盖全部 3 个产品的 Top3=100% 解释成“少数头部集中、尾部微弱和集中风险”。数据没有给出阈值或风险标准，且三个产品的毛利份额并无单一头部垄断。该例提供了设备任务之外的同类失效模式：描述统计被改写成没有判据的业务评价。它还不能证明当前代码仍会如此，因此当前版本 verdict 仍为 not evaluated。

事实基线、验收范围及复跑限制记录在 `docs/runtime-cross-task-acceptance-matrix-20261008.md`。当前代码表达阶段的隔离首轮已使用留存 CSV 独立重算事实并保存原始请求/响应；没有执行提交工具或改写历史记录。它只覆盖表达阶段，不是当前全链路复现。仍不使用语义校验、模型复审或自动重试来提高通过率。

当前表达阶段已用留存请求和 CSV 做完一次隔离首轮：表达上下文/契约来自当前代码，销售、成本事实由 CSV 独立重算；历史报告未进入输入；没有执行提交工具、没有数据库写入、没有 Evidence、没有复审或重试。22.578 秒，8,999 tokens。主要金额、产品排序、占比、销量及成本均匹配事实，且没有复述旧报告的“集中风险/亏损边缘”；但仍生成“定价策略导致毛利率差异”“以量补价”以及“完整月份数据”等缺乏因果或总体完整性依据的说法。故该任务族当前表达准确性仍失败，完整 pipeline 未测。详细事实与原始请求/响应保存在 `docs/runtime-cross-task-acceptance-matrix-20261008.md` 指定的目录。

这把问题进一步收敛到设计责任，而不是输入事实或之前的历史回归结果：当前 `expression_scope` 已为 descriptive-only、决策条件为空，真实汇总也已可见，但自由正文仍自行补充原因和完整性。新的提示禁令同样不能构成可靠边界。下一步先做设计审查：现有事实/语义执行契约如何表达“描述事实、数学推论、已声明业务判据、因果结论、数据覆盖声明”之间不同的证据来源，表达阶段如何把无依据的业务主张留在事实范围内；设计必须不依赖语义审核/重试，也不能用额外模型调用换准确率。还需解释其自然报告质量影响和每轮成本，然后才对两个任务族各做一次当前表达复验。未通过该设计门槛前不跑高成本的全流程或 Evidence，也不宣称准确性收敛。

代码审查把“证据身份与叙述生成权分离”具体化：`SemanticExecution` 持久化的 `DecisionRef` 目前以 max/min 数学极值为主；值级 `evaluate_numeric_comparison`/`render_numeric_comparison` 可计算大小关系和差额，但没有通用的来源绑定 Decision/finding 身份。任意 `PythonCalculation` 在 Evidence 中仍是 `execution_only`，输入公式未被证明；报告片段可以携带数值 lineage，但 `compose_report` 仍接收普通任意字符串，所以这些 lineage 不约束全文语义。相关源代码边界见跨任务矩阵中的 Code-level contract audit。

随后做了不调用表达模型、也不进入生产代码的离线 typed-findings renderer 原型。产品成本案例用 7 个带来源和方法的 finding 生成总览、数学比较、排序、分别展示销量与毛利次序、成本明细及数据覆盖限制，1,204 字符；设备案例用同一 finding 类型覆盖原始 7 组事实，1,348 字符。设备事实从被选 Excel 本地重算，7 组与 r19 Worker 保存的值全部相符。两个输出保留了当前问题涉及的全部计算维度，删去了报告中无依据的业务解释；因此文字更短但统计覆盖没有缩减。原表达调用约 20 秒级、每轮约 13k tokens（设备 r19）或 9k tokens（产品），确定性 renderer 不产生表达调用；是否由宿主完全代替表达模型，会减少自由叙事，需进一步验证真实报告可读性与产品接受度。这些只证明两类低/中复杂度任务有可读结构化呈现方向，不证明复杂开放式报告可覆盖。

接下来映射生产接口时需要同时解决两处已知边界：一是 `PythonCalculation` 的执行事实缺少可验证的公式/字段 lineage，二是 `compose_report` 允许无来源的自由字符串。需要以可执行的有类型 finding 把 calculation results 与报告段落绑定；值级 comparison 已有 helper，可复用其数学结果，但要补齐持久来源身份与通用发现对象。业务判据、因果方法和总体覆盖必须仍绑定其真实来源，不能把一个 finding 类型变成语义认证器。先做 API/状态生命周期原型和成本估算，再决定是否在生产代码增加执行类型；不通过另一轮表达模型或语义 review 来认证正文。

另发现初版离线原型本身把 `rendered_text` 放在 finding 对象里，故其结构还容许任意断言，不能作为边界实现。第二版改为 Pydantic discriminated finding 类型，并移除了正文文本字段；当前未知字段会被拒绝。两任务报告长度分别 1,109/748 字符，包含所有已计算维度但明显更紧凑、叙事更少。它依然有可任意填写的标题、指标标签及嵌套 dict，且没有把 findings 绑定到运行时执行 receipt，所以还不能作为可靠实现。下一步先让原型只接受 Schema/注册表的标签引用、正式 result IDs 和受支持操作，再验证宿主能否拒绝自由字符串主张且不做自然语言语义判断；如果字段身份/操作类型覆盖不够，增加最小通用执行原语，而不做案例分支。
