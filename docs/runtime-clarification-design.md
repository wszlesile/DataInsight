# Runtime 同轮次澄清设计

## 1. 设计目标

同轮次澄清用于处理一种窄而关键的情况：一个会实质改变答案的业务定义存在互斥解释，
而用户问题、会话规则、完整 Schema 和可执行 Probe 都不能唯一确定。澄清不是独立分析阶段，
也不负责提前规划指标、查询、图表、表格或报告。

## 2. 语义所有权

统一 Runtime 始终是查询、计算、产物和报告表达的唯一语义所有者。它在同一个 ReAct
上下文中决定三种动作：

1. 信息充分时直接生成正式分析代码；
2. 枚举、格式、时间覆盖、查询路径或有无数据不确定时，生成有界 Probe；
3. Probe 也无法消除关键业务定义歧义时，调用 `request_analysis_clarification`。

不存在 Runtime 前的第二个语义规划器，也不存在一份必须由 Runtime 照抄的指标边界清单。

## 3. 澄清契约

澄清工具只输出交互所需信息：

```json
{
  "items": [
    {
      "item_id": "time-attribution",
      "ambiguity_kind": "time_attribution",
      "subject": "批次统计周期归属",
      "question": "批次按开始时间还是结束时间归属统计周期？",
      "options": [],
      "allow_free_text": true
    }
  ]
}
```

工具是终止型工具。调用后当前 Agent 图结束，任务和轮次进入
`waiting_clarification`。用户可选择快捷项或直接补充文本，原任务、原轮次随后恢复。
该挂起协议只适用于具有持久化任务 ID 的异步分析链路；旧的同步调用没有可恢复任务时，
工具退回普通对话式澄清，不创建无法恢复的等待状态。

恢复时，后端按 `clarification_id + item_id` 保存并恢复用户回答，保留问题、用户文本、快捷
选项对应的完整含义和原始语义范围。后端不把回答再次编译成实体粒度、总体、分子分母、时间
归属、公式或 Probe 要求，也不从 Schema 或模型常识补写用户没有确认的内容。Preparation
快照沿用暂停前已完成的结果，不重复选源和关系分析。

这里的“指标规划”是指新增用户未要求的报告指标。用户已经明确点名的业务指标如果缺少权威
定义，可以澄清其总体、粒度、分子分母、时间归属或业务公式；用户回答作为业务事实恢复到
Runtime，但系统不能据此生成一份限制后续洞察表达的指标清单。

用户回答属于权威业务事实，但仍由恢复后的同一个 Runtime ReAct 负责把事实落实为查询、计算
和报告。执行前不再调用第二个 LLM 编译或审核代码，也不通过搜索 Probe 代码中的字段字面量
判断事实是否已经落实。系统只保留语法、安全、字段归属、显式时间范围、查询能力和产物结构等
能够确定性证明的本地契约；业务语义由 Runtime 在完整上下文中统一判断。

## 4. Probe 与澄清边界

以下问题由 Probe 解决：

- 字段真实枚举、编码和非空样例；
- 日期或标识的存储格式；
- 时间覆盖、查询路径和数据是否存在；
- 已知关系在当前数据上的覆盖情况。

以下情况才允许澄清：

- 多个业务总体都合理，但精确答案必须选择一个；
- 开始与结束时间都可能作为业务归属，且没有权威规则；
- 分母、比较基准或业务公式存在互斥定义；
- 存储值可探测，但其业务含义没有权威映射。

能够并列计算、分别披露或透明说明限制时，Runtime 继续分析，不中断用户。

## 5. 性能与稳定性

- 正常分析不增加任何 LLM 调用；
- 澄清恢复只重新进入统一 Runtime，不增加语义决策编译或代码审核 LLM；
- Probe 与正式代码修复继续共享同一 ReAct 消息历史；
- 澄清回答只注入一次，后续修复轮次不重复扩张上下文；
- 用户已经确认的业务定义只在澄清回答块中出现一次，不复制到 Probe diagnostics；
- 澄清传输、任务挂起和恢复由后端结构化协议保证；
- 业务语义正确性不由本地关键词或文本正则重写。

## 6. 验收标准

- 信息充分的分析直接进入 Runtime，不出现固定的语义阶段耗时；
- 技术未知先 Probe，关键业务歧义才澄清；
- 用户回答后不重复 Preparation，也不重复询问；
- Runtime 保持完整洞察表达能力，报告不是指标说明书；
- 已确认的总体、分子分母、时间归属或公式必须由可执行代码落实，不能只在报告中复述；
- 澄清机制不改变正式分析、图表表格和后置 Evidence 的契约边界。
