## 1. 对此前判断的修正

不能再采用“架构方向已经正确，剩下都是实现细节”的前提。

保留 Preparation -> 统一 Runtime ReAct -> 后置 Evidence，是职责边界选择；它并不证明当前
Prompt、工具和反馈的具体方案足以达到准确性目标。此前方案对减少机械错误有具体机制，
对首份程序中的业务误解主要依赖原则性提示，两者之间没有形成已经验证的因果链。

因此要分别判断：

1. **目标覆盖不充分**：只有较短 Prompt 和更好的修复，不能解决所有首次业务理解错误。
2. **设计尚未落实/证实**：按需参考仍未实现，减少首包压力的收益也不能预先承诺。
3. **实际实现丢失信息**：规则在源上下文存在，却没有传到模型；本轮找到确定实例。
4. **新改动引入回退**：提前结束 ReAct、审核误报、失败查询伪装空表等，不能归咎于模型。
5. **信息充分后模型仍误用**：需要隔离评测，既不能宣称已解决，也不能笼统归为模型不聪明。

## 2. 本轮最重要的新发现

### 2.1 可查询 Schema 完整，但知识参考的字段定义丢失

`PreparationResult.prompt_snapshot()` 把选为 `semantic_reference_datasource_ids` 的来源从
物理查询集合移出，这是合理的。但它只向 `analysis_semantic_context.semantic_references`
复制 ID、名称和整体 description，未复制 `metadata_schema`。

冻结输入 `prepared-48-70.json` 包含 14 个选择结果：13 个物理来源、1 个知识参考。
这不是最近在十三个物理来源中漏选了一个表。原有知识参考有 12 项字段定义，其中包括：

- 低侧超限量为 `spec_lower - test_value`，低于下限时才为正。
- 高侧超限量为 `test_value - spec_upper`。
- 批次上下文的一行代表一个批次，根因候选的一行代表一条检测结果。
- 批次计数和检测计数的唯一键、周期归属字段。

实际 r16 模型输入只保留了该知识参考的总描述，以上细化定义不在请求中。
十三个物理来源的 230 个字段定义在忽略空 example 的等价简写后全部保留。
此前审计以“参考名称和总描述存在”判断语义内容没有丢失，不充分。

`git show HEAD:src/agent/analysis_preparation.py` 确认该缺口在已提交基线就存在。
因此它是应该修复的基线能力缺陷，不是本次 Prompt 拆包独有的问题。

### 2.2 与错误的关系以及不能夸大的部分

r16 首份正式程序在低侧返回 `(test_value - spec_lower) / span`，随后按带符号值求 max、
降序，漏掉偏离幅度更大的低侧检测。独立查询得到低侧 11.7535%，报告选了高侧 11.3667%。

这里能证明的是：**有用的明确规则被系统丢失，而且最终代码与被丢失规则矛盾**。
不能仅据此证明恢复规则后模型一定正确，更不能声称包装代理、物料风险、报告表达也会自动修好。

包装问题同时存在信息质量与消费问题：普通异常单字段描述提到“批次、班组或包装链路”，
但这不意味着所有异常单都是包装问题；另一个已给出的来源含明确包装风险字段。
模型把 `nonconformance_count>0` 直接称为包装因素，没有获得这种等价关系的依据。

### 2.3 本轮修复及边界

- 在既有 `semantic_references` 中完整保留原始 `metadata_schema`，不生成指标计划或新公式。
- 仍不把知识参考加入可查询来源、JOIN、used_datasource_ids。
- 保持原始字段、规则、适用对象、未知/冲突信息，不把知识来源升级成比用户更高的权限。
- 澄清挂起/恢复继续使用同一 Preparation 快照；新增测试验证恢复后信息仍完整。
- 增加一条实际协议说明：知识参考里的 Schema 用于解释事实，不是要求查询的事实表。
- 不调整 Selection/Business Context 的选源、关系分析职责，不新增校验、模型调用或重试。

真实冻结输入离线重装配确认 12 项定义恢复，仍只有 13 个物理来源。
新增内容约 2,220 字符，是补回已有信息的必要成本，不把它包装成性能优化。

## 3. 按根因评估方案是否有效

| 根因类别 | 已有证据 | 哪类机制真正相关 | 当前结论 |
| --- | --- | --- | --- |
| 原信息没有唯一业务定义 | “本周期”具体期间、根因综合排序规则未必唯一 | 同轮次澄清；可并列解释时透明说明；已有规则优先 | 澄清机制有针对性，但不能替代算法能力 |
| 信息存在但传递损失 | 本轮发现知识参考的字段规则丢失 | 无损传递、最终请求逐项核对 | 本轮已修，真实模型效果待验 |
| 已有事实被误当代理 | 普通异常单等价包装、物料数多等价风险 | 核查字段定义与实际使用；隔离首份代码的语义消费测试 | 更好的错误定位不会直接解决 |
| 数学/粒度实现错误 | 基线物料计数重复；r16 带符号值错误排序 | 对独立预期结果检验程序；完整信息下评估模型实现能力 | 不能把能执行、能溯源当准确 |
| 工具/反馈不一致 | Probe 失败变空表、修复坐标与版本混淆 | 稳定 API、真实错误、同一程序版本和 ReAct | 有确定修复和局部测试，不等于所有业务通过 |
| 上下文/接口认知负担 | 约 16 万字符首包、多种重复描述、整份程序生成 | 分层、去重、可执行用法、有限对照实验 | 有合理依据，未证明是语义错误唯一原因 |
| 新机制误伤 | return_direct、LLM 审核假矛盾、模糊静态推断阻断 | 撤销误伤机制，不扩大重试和判定权限 | 已删除/修复；不能继续用同样方法兜底准确性 |

不同错误持续出现，不必然说明每个问题都是孤立缺陷。它们反映至少三类不同断点：知识交付、
代码语义实现、执行与反馈。若只修最后一类，前两类仍会在每轮以不同业务字段表现出来。

## 4. 调研重新校准

只使用可核查的一手资料，不以“主流 Agent”证明本方案最优。

- Anthropic 同时提醒避免过于笼统的指导和堆叠分支规则，强调清楚的工具、必要上下文、
  有代表性的示例；minimal 不等于 short。分文件并不自动产生这些效果。
  [上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Snowflake VQR 用已核实的问题/查询及语义定义支撑正确性，并提醒错误示例反而有害。
  可借鉴的是知识依据与独立验证，不是强制每轮报告填固定指标表。
  [VQR](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)
- OpenAI 将轨迹定位问题和可重复数据集对照分开。我们的多次真实运行有诊断价值，
  但跨时间范围、多个改动、单次随机生成的结果不构成因果对照。
  [Agent 评估](https://developers.openai.com/api/docs/guides/agent-evals)

推论：当前统一语义职责可继续保留，但“Prompt 拆包 + 修复工具”只能作为部分方案。
业务知识到模型的无损交付、模型到计算的可靠性必须单独证明；资料没有保证任意小模型一次成功。

## 5. 实际上下文与设计可落地性

r16 保存的实际 SystemMessage：

| 内容 | 字符数 | 含义 |
| --- | ---: | --- |
| 整体 SystemMessage | 162,785 | 不含全部后续 ReAct 消息 |
| 事实信封 | 139,123 | 包含业务准备、来源 Schema、环境能力 |
| 数据源部分 | 106,155 | 不只纯字段文本，也含来源和关系元数据 |
| analysis_semantic_context | 32,345 | 业务问题、血缘、参考等 |
| 技术协议包 | 19,328 | 全部相关包一次注入 |

技术协议约占 SystemMessage 的 11.9%。即使将其全部移除，也不能将首次输入压成小 Prompt；
这也不是允许移除协议的理由。保留完整 Schema 的要求与“任意规模都保持很小首包”不能同时保证。
之前以删减技术文本作为主要性能与准确性杠杆，收益预期需要收敛。

模型输入 token 随轮次为 53,740 / 61,072 / 73,434 / 79,568。
最后一次生成完整正式程序耗时约 90.5 秒、输出 8,009 token。
因此还存在长程序输出与连续观察增长成本，不能把全部延迟归因于输入或网关。

审计时 `runtime_prompt_loader.py` 完整装载相关协议，registry 没有已生效的按需阅读动作。
同时 `_load_runtime_contract_body()` 移除完整示例；当前的局部行为测试验证 API 可调用，
不验证模型能从分散片段可靠组织整份分析。现有隐藏示例还含未说明依据的 50% 集中度判断，
不能为了“恢复示例”直接全部打开。保留、替换或延迟加载必须独立测试。

另发现实际 r16 末尾附带“刷新回复可自行判断普通问答”的指令，与正式 Runtime 已完成分流的
定位不一致。该提示在基线也存在。它是待处理的上下文职责错位，但本次 r16 仍进入正式代码，
不能拿它解释已出现的排序算法错误。本轮没有顺带修改该路由。

## 6. 下一步只做可区分的增量

本节 A-D 是效果评估次序，不是用复跑替代设计。补充后的实现决策和进入复跑的门槛见第 8 节；第 8 节的工程门槛未完成前不发起真实回归。

### A. 先修已证明的信息损失

本轮已做知识参考 Schema 的无损承接。继续以输入来源 -> prompt_snapshot -> 最终模型请求
检查知识和用户澄清，不再只按字段/API 名称做存在性检查。来源已有规则不得由模型重新摘要后替代。

### B. 单独评估知识恢复的效果

使用当前同一执行底座、相同物理来源/模型/历史/数据期间，比较旧知识投影和完整知识投影。
旧投影只在隔离评测里复现，不能在业务入口加降级开关。
保存首次程序和全部失败；独立核算符号/幅度、计数粒度、来源替代及报告结论。
知识恢复若仍不能改善相关错误，要如实判为“必要但不足”，不能继续声称只是还需重试。

### C. 再隔离上下文与 API 的影响

- 信息、工具与执行器不变，只比较上下文编排/用法说明；不要同时改返回类型和 Probe 规则。
- 对已知错误族做独立小任务诊断：完整字段定义下能否选对事实；已知输入下能否正确计算。
  小任务只用于定位，不引入正式流程的新语义 Stage，不把小任务通过当整题验收。
- 简化诊断也失败时，说明“再整理 Prompt 就够了”的假设不足；需要重新评估算法实现方式或模型适配。
  简化诊断稳定、完整任务失败时，才有依据优先研究上下文组织/任务负担。
- 当前协议不变下加入一种经过验证的组合示例做独立实验；不规定报告模板，不写会话字段特例。
- 将常驻必需协议进一步迁出首包，需要先证明它是瓶颈。本轮只补齐原本被省略的完整示例的可达性，
  并未迁出必需协议，也不以参考工具已上线声称首包或总耗时下降。

### D. 机制去留必须有结束条件

每个机制先做一个明确对照，代表问题重复测试并保留失败，再到独立问题检验泛化。
初步每组至少三次仅作筛查，不声称统计证明高可靠性。两个限定的候选实验都没有改善目标错误族，
停止该方向并重审机制，不叠加第三层补丁。负向变化按实验边界撤回，不整体回滚需求。

准确性和表达力不能互相补偿；速度改善不能抵消关键计算错误。基线本身错误需独立金标准核实，
“比基线好”与“达到业务验收”都要检查。只有前述诊断收敛后，才恢复空间 15 顺序整体验收。

## 7. 本轮验证与保护范围

- properties 与 fields 两种元数据输入、恢复后的最终模型消息、源快照不被修改均有测试。
- `.codex-regression/runtime-comparison/audit_design_evidence.py` 离线检查 r16 保存的实际请求；
  `design-audit.json` 同时记录旧投影缺失的 12 项定义和当前离线重装配全部保留的结果。
- 该脚本不执行保存的分析代码、不调用模型、不查询数据库；不是整体验收。

结论不是“方案已无问题”，而是：**现在有一个已证实的基线知识交付缺陷，同时原方案对准确性
的覆盖和验证方式仍不足。先修复真实断点，再验证具体机制，不能再用架构名称正确替代效果证明。**

## 8. 复跑前的方案定稿与工程门槛

### 8.1 选择的方案

保持 `Preparation -> 单一 Runtime ReAct -> 后置 Evidence`，不增加语义审核、指标计划或报告模板 Stage。
在这个边界内采用 **完整业务依据常驻、必需协议直接交付、详细用法可查阅、同图执行修复**。
这不是全新业务大对象，也不把正式程序拆成多个互相承接的语义产物。

方案选择依据：

| 选择 | 已知缺陷与机制 | 不采用的替代方案及原因 |
| --- | --- | --- |
| 完整事实直接交付 | Schema、知识定义、关系状态和用户答案必须到达实际请求；不能只检查名称存在 | 不把 Schema 摘要化、再让模型猜回字段和公式 |
| 常驻必需协议 + 本地参考工具 | 首次即可执行；复杂组合用法可在同一 ReAct 批量查阅，文档增长不必全部进入首包 | 不要求每次先读文档，不用协议加载校验再制造重试；也不照搬某厂商专属 Tool Search API |
| 示例与实现共同测试 | 除函数签名外，还核验示例得到的数值、条件分支和产物；示例不能凭空产生风险阈值 | 不用唯一报告模板限制分析；不把隐藏的完整示例误算成模型已获得的能力 |
| 路由决定单一来源 | 已分流到分析的刷新请求不能再被末尾提示改成普通问答 | 不让是否曾经成功执行决定本次是否是分析任务 |
| 稳定工具闭环 | 查询失败、成功空集、有效数据分开；补丁对齐同一源码版本；原始观察留在当前 ReAct | 不增加成功后 LLM 阻断审核，不把 unknown 当错误，不用空表掩盖异常 |
| 依据驱动的计算与叙事 | 使用已有定义和真实计算形成判断；明确的算法与缺失的业务定义区别处理 | 不让 Preparation 定指标，不依靠增添业务字段特例和禁止语句达到准确性 |

这比基线的改进有具体因果依据：补齐已经丢失的事实，消除已证实的相互冲突指令，降低机械重复，
给模型可查的正确组合用法，并保持错误与上下文连续。不能由此推导任意模型对任意业务问题都必定正确，
也不能承诺之后只会遇到实现细节。真实验收是检验此方案，而不是只允许证实此方案。

### 8.2 参考主流机制的取舍

- Anthropic 提倡清晰且少重叠的工具、可操作示例和高信息密度反馈；采用组合查询、真实错误和可执行用法。
  [工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Anthropic 的混合上下文方式同时考虑预先交付与按需检索的延迟；采用完整事实常驻和可选参考，不迁走业务 Schema。
  [上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- OpenAI Tool Search 展示了延迟发现能力的机制；本项目借鉴“可发现且可读取”，不更换当前模型、API 协议或网关。
  [Tool Search](https://developers.openai.com/api/docs/guides/tools-tool-search)
- Snowflake 使用经过核实的语义定义和查询示例帮助准确性；本项目保留现有知识来源，测试通用机械示例，
  不把单个业务会话 SQL 固化成产品知识，也不把 SQL 专用语义层强加给文件和时序分析。
  [Verified Query Repository](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)

上述资料支持机制选择，不提供当前模型或本项目准确率的保证。

### 8.3 本轮实现范围

1. 继续保留已完成的知识参考 Schema 无损承接及恢复测试。
2. 刷新提示显式消费已经确定的分析/普通问答分流结果；invoke 与 stream 两条入口一致。
3. 增加只读 `read_runtime_reference`：按注册 ID 批量读取完整协议与组合示例，在原 ReAct 返回 ToolMessage。
   不读取任意路径、不访问数据、不生成业务事实、不记录一次 Python execution，也不触发 no_data 或 Evidence。
4. 参考目录与现有 Contract Pack 同源。初始必需协议、混合查询能力并集、输出模式及澄清策略不变。
   模型只在需要组合用法时读取，不能要求先读才可执行。参考不是输出策略的第二来源。
5. 修正完整示例中无依据的 50% 集中度结论，用真实排序、差值、份额、可比较性产生动态说明；
   覆盖并列、单组、零分母、负值等边界。示例只是机械演示，不作为业务公式金标准。
6. 用真实 Agent 图的脚本模型测试参考查阅、Probe、失败修复、澄清策略及保存后的终止，检查连续消息而非只查 API 名称。
7. 移除本地根据 `unresolved_facts` 为空便暗示语义已完整的提示。完整准备事实照常交付，是否有实质歧义仍由统一 Runtime 判断。
8. 字段范围说明对齐实际 `allowed_fields_ref=metadata_schema.properties` 投影；保留显式 `allowed_fields`，不要求模型重复构造同一字段清单。

不修改 `.env`、远端服务、模型参数、Selection/Business Context 的职责、正式分析的范围、Evidence 计算或既有外部接口。

### 8.4 准确性的责任边界

- 输入缺失：通过最终请求的事实保真测试解决，不交给重试碰运气。
- 已有业务歧义：由同一 Runtime 结合上下文判断；Probe 能确定的技术事实先查证，确需用户决定时才澄清。
- 算法实现错误：用完整定义、可执行组合用法和原图内真实错误帮助实现；验证必须有独立预期值，
  不能用同一生成公式重复计算“证明”自己，也不能让 Evidence complete 冒充算法正确。
- 证据到判断：事实、代理信号和因果结论不同；计算更多指标本身不能解决无依据的等价替换。
  不新增本地文本语义分类器，也不建立自动强制评分、风险阈值或后置审核闭环。

静态审查可证明信息交付和协议一致；不可证明模型永远正确理解。方案在机制上覆盖已知原因，
仍必须接受后续独立业务验收的否证。此边界不是允许继续随机复跑，而是明确设计论证与效果证明分别负责什么。

### 8.5 完整性和性能门槛

- 所有必需事实原样保留；引用知识不是物理表；用户答案在挂起恢复后不丢失。
- 关系、时序、文件及混合场景，核心协议和可选参考共同保持能力完整；没有“文档有、模型不可达”。
- 新参考工具没有固定模型调用成本；读取本地文档不产生网络查询或执行记录。自愿查阅仍会增加模型回合，需单独统计。
- 不以协议包字符数代替最终请求 token；当前约 16 万字符事实请求不能靠缩短 1.9 万字符技术说明解决。
  完整业务 Schema 常驻的约束意味着首包存在下限，不承诺任意规模常数上下文。
- 不改写或压缩当前 ReAct 的原始错误和程序；将来若需要压缩，另行设计可恢复机制并单独验收。
- 同轮次澄清、外部 standard/text/json、取消、Probe/no_data、参数重跑、源码修复及后置 Evidence 隔离测试通过。
- 工程门槛通过后，才进行固定输入和独立计算预期的真实对照；不再一轮改多个机制后按耗时判断因果。

本节取代“马上再跑一轮看看”的推进安排。交付工程验证结果后，再确认进入真实回归；不宣称业务验收已完成。
