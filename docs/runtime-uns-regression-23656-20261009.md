## 结论与推进顺序

1. type 1 的访问协议能够执行，但其多源路径性能仍不稳定；三次等待约 95 秒的超时将一次趋势请求拉长到约 11.5 分钟。应先检查技术超时的具体调用和重试边界，再改运行时并复跑同一原轮次。不能以减少数据源或分析范围作为性能优化。
2. type 3 与 type 7 的共同环境故障是 `uns_timescale` 中物理关系别名缺失。两者都通过时序查询协议访问，type 7 的目标 type 1 独立复现同一问题。当前证据不支持通过改用 `uns_get` 来绕过故障；应修复 UNS 导入/别名注册与查询端可见关系的一致性，或在目标环境恢复该关系，再复跑。
3. type 2、type 9 在该环境完成真实查询和产物生成。type 9 表格与图表数值来自同一 4 行查询，报告引用了主要数值；自然语言建议对近半数记录为 failed 的结果仍称整体稳定性较好，属于报告解释质量问题，需由分析模型在规划和结果上下文中表达准确，不以语义校验重试弥补。
4. 本地来源归属改动需要部署到回归环境后，再刷新 type 1 原轮次确认来源消费记录。type 3/7 的别名可用后也按同一轮次或独立样例复跑，核验真实读取、Evidence、报告引用和耗时。
